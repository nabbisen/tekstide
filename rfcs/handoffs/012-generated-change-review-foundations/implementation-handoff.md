# RFC-012: Generated Change Review Foundations - Implementation Handoff

## Scope

Implement headless generated-change review foundations only after RFC-012 design review accepts or amends the policy.

The implementation must preserve RFC-010 AgentRun lifecycle truth and RFC-011 transcript privacy boundaries. ChangeSet review state is generated-work review metadata, not process supervision, audit persistence, rollback, or test evidence.

## Existing Anchors

- `crates/tekstide-core/src/domain/changeset.rs` already provides `ChangeSet` and `ReviewState`.
- `crates/tekstide-core/src/domain/agent.rs` already provides `AgentRun::change_set_ids`.
- `crates/tekstide-core/src/project/session.rs` already owns `ProjectSession::add_change_set` and derives review-ready counts from unreviewed ChangeSets.
- RFC-006 root-bound file access remains the project-root containment baseline.
- RFC-010 owns AgentRun launch and lifecycle.
- RFC-011 owns transcript byte retention and privacy boundaries.

## Hard Requirements

- No file contents, diff hunks, transcript snippets, prompts, environment values, or shell history in summaries or errors.
- No path outside the ProjectSession root may be reported as an ordinary in-project changed file.
- No overclaim that a ChangeSet was generated by an AgentRun when the association is ambiguous.
- No review-state transition may edit files, delete files, run commands, revert changes, or imply tests passed.
- No durable audit persistence in RFC-012; RFC-013 owns durable audit.
- No rendered diff/review UI in RFC-012; M8 owns real GUI review surfaces.
- No search indexing, secure deletion, or redaction guarantee.

## Model Guidance

Prefer extending existing `ChangeSet` vocabulary before adding a parallel review entity.

Expected additions:

- review baseline metadata;
- detector source/status;
- association confidence or equivalent authorship caveat;
- bounded changed-path summary;
- artifact references that do not contain file contents;
- explicit review-state transition helpers;
- ProjectSession operations for AgentRun-linked and unlinked generated changes.

Use domain-specific submodules if `domain/changeset.rs` or `project/session.rs` becomes too large. Do not force a split before implementation boundaries are visible.

## Detector Guidance

Start with metadata-only detection.

Acceptable first detector approaches:

- Git status metadata where available;
- filesystem baseline comparison for tests and non-Git projects;
- explicit caller-provided project-relative paths from a reviewed harness.

Detector results should state whether detection was complete, unavailable, partial because limits were hit, unsupported, or failed with bounded diagnostics.

If Git detection uses a subprocess, the implementation must use a reviewed non-project-local Git executable, invoke it directly without a shell, avoid Git aliases, avoid project-local `PATH` preference, pass a sanitized environment, avoid workspace hooks/config automation, bound timeout/output, and return content-free diagnostics. If those guarantees cannot be met, report Git detection as unavailable or unsupported and fall back to metadata-only filesystem detection where available.

A safe library implementation can satisfy Git detection without subprocess launch claims, but review must verify metadata-only behavior and no workspace automation execution.

## AgentRun Association Guidance

Strong association requires a baseline captured for a specific AgentRun and a scan after that AgentRun reaches completed, failed, cancelled, or review-ready state without overlapping ambiguous runs.

Detached or orphaned AgentRuns are weak or ambiguous unless a later reviewed runtime policy has independent evidence that the process boundary is closed and no overlapping run can own the same changes.

If association is ambiguous, create an unlinked or weakly linked ChangeSet. Do not attach the ChangeSet to `AgentRun::change_set_ids` as fact unless the implementation can defend that association.

## Review Request Requirements

Every implementation review request for RFC-012 must reference:

- `rfcs/done/012-generated-change-review-foundations.md`
- this handoff pack;
- relevant prior RFCs: RFC-006, RFC-010, and RFC-011 at minimum.

Implementation review request filenames should include `implementation`.
