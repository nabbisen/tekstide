## Scope

RFC-021 defines the command approval model and adapter capability contract. Headless; the rendered dialog is RFC-022.

Evidence in this file must not be used to claim command-level enforcement, OS-level interception, approval for `Plain`/`Supervised` runs, pattern-based auto-approval, a rendered approval dialog, or that any specific AI CLI supports the adapter contract — unless later reviewed implementation explicitly supports that claim.

**Standing constraint on all wording here:** approval is a *cooperative protocol*. Tekstide cannot intercept what a spawned process executes. No entry in this file may imply otherwise.

Per the handoff README, PR-021-A (design/handoff acceptance) is treated as already granted, and PR-021-B..E are authorized to begin immediately and headless, in parallel with RFC-014.

## Implementation Evidence

### PR-021-B — Protocol types and validation

**Module:** `crates/tekstide-core/src/approval/` (new top-level module, `approval.rs` + `approval/protocol.rs` + `approval/tests/protocol.rs`), registered in `lib.rs` alongside `agent`/`audit`.

**What exists:** `CommandProposal` and `CommandDecision`, the two RFC-021 sideband messages, each constructed only through a fallible, validating decoder (`CommandProposal::decode`, `CommandDecision::decode`). There is no way to hold an instance of either type that has not already passed every bound and shape check — deliberately stricter than `audit::record::DurableAuditRecordV1`, whose `validate()` runs as a separate step after construction. That type is built from already-trusted, internally-generated data; these two cross an untrusted boundary from an adapter process, so parsing and validating are one inseparable step here.

**Scope boundary, stated explicitly so it is not mistaken for an oversight:** this slice does not decide whether a token is the *correct* token for a run, whether a proposal id has been seen before, or whether a cwd stays inside the project root. None of that is decidable without context (the real per-run token, prior proposal ids, the project root) that a pure protocol decoder does not have. Those checks belong to `approval::channel` (PR-021-D) and `approval::coordinator` (PR-021-E), and are deliberately left for those slices rather than reached for here.

**argv is a vector, not a shell string, by construction — not by a runtime check.** `CommandProposal::decode` and `CommandDecision::decode` both take `Vec<String>`; there is no code path, in this module or its callers, that could pass a single shell string through this API and have it split into arguments here. The actual "reject a shell-string proposal rather than split it" requirement therefore has to be honored by whatever wire-decoding layer PR-021-D builds (deserializing the raw adapter message into this vector) — that layer must reject a message that supplies a string where the schema calls for an array, not attempt to tokenize it. Recorded here as a boundary condition PR-021-D must satisfy, since PR-021-B's type signature makes the alternative unreachable but cannot make the *wire* format decision.

**Bounds chosen** (all `pub const` in `approval::protocol`, revised per response 109 — see follow-ups below): proposal id and token ≤128/256 bytes respectively, restricted to printable ASCII (`is_ascii_graphic`) so either can be logged or compared without interpretation; argv ≤512 entries of ≤65536 bytes each **and** ≤1 MiB total across all entries combined, no embedded NUL (a NUL cannot appear in a real argv entry passed to `exec`, so its presence is a malformed/adversarial signal, not a legitimate argument) but otherwise permissive of arbitrary content, since Tekstide does not interpret shell grammar; cwd ≤4096 bytes, must be absolute, no embedded NUL; declared intent and declared effects ≤512 bytes each, no control characters (control characters in text a future GUI dialog will render verbatim are a display-spoofing vector in their own right, independent of the RFC-009 terminal-escape concern).

**Empty-string argv entries are accepted**, not rejected. Real commands legitimately take one (`printf '%s' ""`, `grep "" file`, a script passing an empty string as an unset placeholder); the security property that matters is that argv is a vector at all, and entry non-emptiness contributes nothing to that. An initial version of this slice rejected empty entries as a precaution; response 109 Q2 concluded that was a net cost with no corresponding benefit (no constructible attack requires an empty entry, while a rejected proposal pushes users toward routing around approval), and asked me to relax it. Done.

**`UntrustedEffectsHint`** wraps the adapter-declared-effects field so the RFC's rule ("a proposal claiming 'read-only' is a hint for display, never a basis for skipping approval or lowering risk") is visible at the type level: the only accessor is `as_str()`, there is no way to parse it as structured data, and it is a distinct type from the plain `String` used for `declared_intent`. This is type-level groundwork, not the full guarantee — the guarantee is only complete once PR-021-C's risk classifier is built and demonstrably never takes this field as an input, which this slice cannot itself demonstrate.

**`RunCapabilityToken` has a hand-written `Debug` impl that never renders the token value** (`RunCapabilityToken(<redacted>)`), tested directly (`token_debug_output_never_contains_the_raw_value`). This exists because the token is a secret credential per the RFC's "Token leakage" risk, and an accidental `{:?}` in a future log statement should not be able to leak it.

**Tests:** 35 tests in `approval::tests::protocol`, covering: valid decode (with and without optional display fields) and preservation of every field; unsupported protocol version; empty/oversized/whitespace/control-character token, plus an at-the-bound acceptance case; empty/oversized proposal id; empty argv (the zero-entries case, still rejected), too-many-entries, at-the-bound acceptance, oversized entry, NUL-containing entry, a normal entry containing spaces and quotes (demonstrating the "vector, not shell string" property does not require rejecting ordinary punctuation), an accepted empty-*string* entry, and an over-total-size proposal built from entries each individually under the per-entry bound; relative/empty/oversized/NUL-containing cwd; oversized and newline-containing intent; oversized effects hint; every `CommandDecision` combination (`ApprovedOnce`/`Rejected` with and without edited argv, `EditedAndApproved` with and without edited argv, edited argv re-validated through the same argv bounds, unsupported version, invalid proposal id).

**Checklist items this slice satisfies, and items it deliberately does not (see below):** argv-as-vector/shell-string-rejection, unknown-protocol-version rejection, malformed-message rejection with no partial parse, oversized-field rejection, and bounded/content-free diagnostics are all satisfied and tested. Duplicate-proposal-id rejection is not — it requires tracking proposal ids across a run, which needs the coordinator (PR-021-E). "Adapter-declared effects never lower risk or skip approval" has its type-level half done here; the behavioral half needs PR-021-C.

Gates run on 2026-07-29 (after the response-109 follow-ups below): `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo test --workspace --all-targets --all-features` (410 `tekstide-core`, up from 375 — 35 new — + 18 `tekstide-gui-spike`, 0 failures), `git diff --check` — all passed.

### PR-021-C — Risk classifier

**Module:** `crates/tekstide-core/src/approval/risk.rs` (+ `approval/tests/risk.rs`), one public function: `classify(argv: &[String], cwd: &Path, project_root: &Path, state_root: &Path) -> RiskAssessment { level: domain::RiskLevel, reasons: Vec<RiskReason> }`. Reuses the existing `domain::RiskLevel` type (`Low`/`Medium`/`High`/`Destructive`, now with `PartialOrd`/`Ord` derived — see response 110 follow-ups) rather than defining a new one, per the handoff. `RiskReason` is new, content-free (no captured paths or argv), and exists per response 110 — see below.

**Design: `Low`/`Medium` are only reachable through an explicit allowlist; everything else is `High` by construction.** The RFC's mandatory property — "unclassifiable input classifies `High`, never `Low`" — shaped the whole function shape, not just one branch: `classify` checks Destructive triggers, then High triggers, then a small `Low` allowlist, then a small `Medium` allowlist, and falls through to `High` if none matched. There is no code path that reaches `Low` or `Medium` without a positive match. The corresponding test (`unrecognized_program_classifies_high_never_low`) is written first in the test file, per the handoff's instruction.

**Path escaping is checked lexically, not via `fs::canonicalize`** — confirmed correct, not merely adequate, by response 110 Recommended 3, which would have rejected a change to real canonicalization here. Every argv entry (except `argv[0]`, see below) is resolved against `cwd` if relative and normalized by manually walking `.`/`..` components — no filesystem access, no symlink resolution — then checked for containment under `project_root` (escalate if outside) and separately under `state_root` (escalate if inside).

**Escalation rules, matching `implementation-handoff.md` §4 plus the refinements below:** path outside project root; privilege elevation (`sudo`/`doas`/`pkexec`/`su`/`run0`, checked by basename and scanned across all argv entries); Git remote-mutating operations (`push` unconditionally, `remote add`/`remove`/`rm`/`rename`/`set-url`/`set-branches`/`set-head`/`prune` but not read-only `remote`/`remote -v`, `tag -d`/`--delete`, `push --force`/`-f`/`--force-with-lease` scoped to `push` specifically); secret-like path patterns matched against resolved path *components*; writes targeting the Tekstide state root. Destructive: `rm`/`rmdir` with a recursive flag, exact-match disk-level programs (`dd`, `fdisk`, `sfdisk`, `parted`, `wipefs`, `shred`, `mkfs`/`mkfs.*`), Git history rewriting (`rebase`, `filter-branch`, `filter-repo`, `reset --hard`), and `git checkout -- <path>`/`git checkout .` (see `WorkingTreeDiscard` below). A shell interpreter as `argv[0]` (`sh`/`bash`/`zsh`/`dash`/`ksh`/`fish`) is `High` unconditionally, regardless of flags. A small opaque-wrapper list (`env`, `nice`, `timeout`, `xargs`, `stdbuf`, `nohup`) is `High` with a dedicated reason.

**Response 110 review, in full — a re-review of this specific slice, not the module in general.** Response 109's discipline (record every finding, apply every required correction, keep every deliberate deviation visible) continues below rather than a fresh writeup, since re-review is what was asked for.

**Mandatory 1 — most of the corpus could not fail, proven by ablation, fixed structurally, not case by case.** The reviewer deleted five escalation rules from the classifier and found every existing test still passed, because `High` was both the escalation target and the fallthrough — a test asserting `High` on `sudo ls` proved nothing, since `sudo` was in no allowlist either way. **Fix: `classify` now returns `RiskAssessment { level, reasons: Vec<RiskReason> }` instead of a bare `RiskLevel`.** Every corpus case that needs to discriminate a specific rule from the generic fallthrough now asserts the specific `RiskReason` is present, not just the level. I re-ran the reviewer's own ablation after the fix (deleted the privilege-elevation rule, re-ran the suite): `ablation_privilege_elevation_rule_is_load_bearing` and the corresponding corpus row now fail correctly, with `reasons` showing `[Unrecognized]` instead of `[PrivilegeElevation]`. This closes the gap permanently rather than only for the cases the reviewer happened to name, since any future rule now needs a corresponding reason for its corpus entry to mean anything.

**Mandatory 2 — attached option values (`--opt=/path`) bypassed containment; fixed, and it exposed a second bug.** `cp --target-directory=/etc a.txt` and `cp -t /etc a.txt` specify the same effect through different syntax but classified differently, because the attached form is not absolute and joins onto `cwd`. Fixed: every argv entry now contributes both itself and (if it contains `=`) the substring after the first `=` as path candidates (`path_candidates` in `risk.rs`). Attached *short* options (`-o/etc/x`) remain uncovered — disclosed, not chased. **While fixing this, the same review found that `argv[0]` was going through the containment check at all**, meaning any adapter that resolves its program to an absolute path (`/usr/bin/git status`) classified `High` regardless of what the command does — an inert classifier in practice. Fixed: `argv[0]` is now excluded from the two containment checks (project-root, state-root) but remains in the elevation and secret-pattern scans.

**Mandatory 3 — `git branch -D`/`-m` classified `Low`; `branch` removed from the allowlist rather than patched.** `branch` was in `LOW_RISK_GIT_SUBCOMMANDS` without checking its delete/rename flags, so `git branch -D main` (which can discard commits reachable only through the reflog) classified the same as `git status`. Per the reviewer's stated preference, `branch` is removed from the allowlist entirely rather than special-cased for delete/rename flags: **an allowlist entry must be a form the code can vouch for *entirely*, including flags nobody enumerated, or it should not be on the allowlist at all.** `git branch` of any kind now falls through to the generic `High`/`Unrecognized` case (never `Low`), which is what "vouch for entirely or not at all" requires. `git tag -d` remains checked explicitly because it is the one flag form the RFC names outright.

**Related, decided deliberately, per the reviewer's request to record the decision rather than leave the inconsistency accidental:** `git checkout -- <path>` and `git checkout .` — the unambiguous "what follows is a pathspec, not a ref" syntax — discard uncommitted working-tree changes unrecoverably (nothing was ever committed, so there is no reflog rescue), which is the same category of data loss as `git reset --hard`. Both now classify `Destructive` with a new, distinct reason (`RiskReason::WorkingTreeDiscard`, kept separate from `HistoryRewrite` since no history is being rewritten). A bare `git checkout <ref>` remains `Medium` — whether an arbitrary bare argument is a ref or a path is not structurally decidable, so only the unambiguous `--`/`.` forms are caught. `git stash clear`/`git stash drop` were also flagged as inconsistent (they purge saved work, similarly to how `branch -D` discarded reachable-only-via-reflog commits) — **left at the generic fallthrough rather than specially escalated**, since stashed work is already a secondary safety net rather than the primary location of uncommitted changes, which I judge as a real but smaller category of loss than discarding tracked-file changes directly. Recorded as a deliberate choice, not an oversight; open to being told this drew the line in the wrong place.

**Recommended 1 (`RiskAssessment`/`RiskReason`) — applied; this is the same change that fixes Mandatory 1, see above, not a separate one.**

**Recommended 2 (over-escalation) — all three applied.** (a) `DISK_LEVEL_PROGRAMS` used `basename.starts_with(program)`, so `shredder`, `ddgr`, and any other program merely *named similarly* to a real disk-level tool classified `Destructive`. Now exact-match against the known program list, plus an explicit `mkfs`/`mkfs.` prefix rule for that one real family of names. (b) Secret patterns were matched by substring-contains against the whole resolved path string, so the ordinary English word "credentials" inside `git commit -m "rotate credentials"` escalated an ordinary commit. Now matched against individual resolved path *components* (exact match for directory-shaped patterns like `.ssh`/`.aws`, suffix match for extension-shaped patterns like `.pem`) — a free-text argument that happens to contain a secret-shaped word as running English text essentially never resolves to a path with that word as its own component. The bare `"credentials"` substring pattern is dropped entirely (`.git-credentials` and a component match on `.aws` already cover the real cases). (c) The `argv[0]`-containment bug described under Mandatory 2 above is the same fix.

**Recommended 3 (wording) — applied.** `acceptance-qa-checklist.md`'s "escalates to at least `High`" line previously said "canonical project root"; the implementation is lexical, and the reviewer would reject a change to real canonicalization here (a proposed command legitimately references paths that do not exist yet). Reworded to "lexical project root containment," and the in-root-symlink case (`cat link/secret` where `link` points outside the root, unresolved) is recorded in Known Limitations: detecting that is RFC-011/RFC-012's job at the point of actual file access, not this classifier's.

**Q1 (shell-interpreter escalation) — simplified per the reviewer's correction.** The `-c`-flag check is removed; a shell interpreter as `argv[0]` is `High` unconditionally, regardless of flags (`bash -lc` now caught the same as `bash -c`, without needing to enumerate flag spellings). The reviewer's corrected framing is recorded verbatim rather than my original: a shell invocation is opaque to structural inspection *full stop* — that is a consequence of the non-goal (not interpreting shell grammar), not an exception carved out of it.

**Q2 (wrapper indirection) — stopped, per the reviewer's explicit endorsement**, plus one small addition: an explicit `OPAQUE_WRAPPER_PROGRAMS` list (`env`, `nice`, `timeout`, `xargs`, `stdbuf`, `nohup`) now classifies `High` with a dedicated `RiskReason::OpaqueWrapper`, rather than these programs merely happening to fall through to `Unrecognized` by accident. Same level as before; now recorded on purpose, which matters once reasons reach a future dialog.

**Q3 (secret-pattern gap) — no action required of this slice.** The reviewer confirmed the handoff's premise was their own error and is recording the RFC-004 environment-variable-redaction gap separately (`rfcs/delivery-plan.md`, not part of this commit). `SECRET_LIKE_EXACT_COMPONENTS`/`SECRET_LIKE_COMPONENT_SUFFIXES` remain local to `approval::risk`, deliberately not merged with environment-variable-name redaction (different pattern kinds: filesystem path components versus variable names).

**Corpus extended** per the reviewer's supplied table (`approval::tests::risk::corpus()`, now 67 cases after both rounds): every previously-non-discriminating `High` case now asserts its specific reason; added `git branch -D`/long-form delete+force (Mandatory 3), attached-option escapes (Mandatory 2, three forms), `argv[0]`-as-absolute-path acceptance (Mandatory 2, two forms), the commit-message/in-root-file secret-pattern-false-positive pair (Recommended 2), exact-match-not-prefix disk-level cases (Recommended 2, two forms), `su -c`/`run0` (elevation completeness), `bash -lc` (Q1 flag-spelling), `env git status` (Q2, `OpaqueWrapper`), read-only `git remote -v` (now `Low`), `chmod -R` (recursive but not deletion — correctly `High`/`Unrecognized`, not `Destructive`), both `git checkout --`/`.` forms, plus (response 111) the remote-verb flag-shift pair, force-push and force-with-lease as `Destructive`, stash-purge pair, `checkout -f`/`--force` pair, and the two `=`-split-scoping cases (free text must not escalate). A dedicated test (`state_root_write_discriminates_only_when_state_root_is_inside_project_root`) constructs the one arrangement — state root nested *inside* the project root — where the state-root rule is non-redundant with the root-escape rule, per the reviewer's specific instruction that any other arrangement proves nothing.

**Response 111 follow-ups (2026-07-29), all applied — re-review, not a fresh review.** Response 111 re-ran the ablation sweep across all nineteen rules individually (not just the ones it had named in response 110) and found seventeen load-bearing; the two exceptions below are exactly what it flagged.

1. **Required 1 — `is_remote_mutating` read the action verb at a fixed index (`argv[2]`), and `git remote -v remove origin` (flag before the verb) classified `Low`.** Git's synopsis is `git remote [-v | --verbose] <subcommand>`, so any flag shifts the verb's position and a fixed-index read misses it. Fixed: scan `argv[2..]` for a mutating verb anywhere, not just at index 2. This is the same mechanism as `git branch -D` (response 110 Mandatory 3) arriving through a different door, per the reviewer's own framing: **moving a program from "unrecognized" into an allowlist transfers responsibility for every argument shape onto the carve-out.** Added fixtures: `git remote -v remove origin`, `git remote --verbose set-url origin u`.
2. **Required 2 — the `git push --force` rule was dead code, and force-push was under-levelled.** Ablating it changed no test outcome, because `push` was already `High` via `ALWAYS_MUTATING_GIT_SUBCOMMANDS` regardless. Separately, and more importantly: `git rebase`/`reset --hard` are `Destructive` because local history rewriting is reflog-rescuable; `git push --force` rewrites history on a **remote other people pull from**, where there is no reflog and the loss is not the operator's alone — a strictly worse case that was classifying one level lower. Fixed: `push` with `--force`/`-f`/`--force-with-lease` now classifies `Destructive` with a new, distinct `RiskReason::RemoteHistoryRewrite` (kept separate from the local-history `HistoryRewrite`, since the loss is categorically different — someone else's clone, not just the reflog). The old `High`-level, push-scoped force check is removed entirely rather than left redundant, since `destructive_reasons` now runs first and would make it permanently unreachable dead code. **`--force-with-lease` is not distinguished from `--force`** despite being genuinely safer (it refuses to overwrite a remote ref that moved since the last fetch) — recorded in Known Limitations as a deliberate simplification, not silently implied to be finer-grained than it is.
3. **Required 3 — `git stash clear`/`drop` classified `High` for the reason `Unrecognized`, not because the level was wrong but because the reason was an accident.** `is_stash_purge` correctly excluded these from the `Medium` stash allowlist, but nothing gave the resulting `High` a name — so a deliberate decision (recorded at length in the PR-021-C write-up above) had zero test coverage of its own mechanism, and removing `is_stash_purge`'s call site would have broken nothing. Fixed: stash purge now explicitly contributes `RiskReason::WorkingTreeDiscard` in `high_risk_reasons` (same reason as working-tree discard via `checkout`, since both are "discard saved-but-uncommitted work," one step removed for stash). Severity unchanged, per the reviewer's confirmation that `Medium` or `High` were both defensible here. Added fixtures and a dedicated ablation-style test (`ablation_stash_purge_reason_is_load_bearing`).
4. **Non-blocking, applied anyway — `git checkout -f`/`--force` is the third instance of the same shape** (`git branch -D`, `git push --force`, now this): a decidable flag on an otherwise-blanket-permitted form. Rather than only recording a Known Limitations line (which the reviewer said would be acceptable), I extended `is_working_tree_discard` to also catch `-f`/`--force` on `checkout`, since the fix is small and the pattern is now well-established across three separate findings — better to close the shape than record a third instance of it. `git checkout -f feature`/`--force feature` now classify `Destructive`/`WorkingTreeDiscard`, the same as the `--`/`.` forms.
5. **Non-blocking, applied — the `=` split now only applies to entries starting with `-`.** Previously `git commit -m "note a=/etc/passwd"` and `echo FOO=/etc/passwd` both escalated, because the value after `=` was checked regardless of whether the entry was option syntax at all. Restricting the split to `-`-prefixed entries keeps every Mandatory-2 case working (`--target-directory=/etc`, `--target-dir=/etc`, `--file=...` all start with `-`) while free text containing a literal `=` no longer escalates. Verified both directions with new fixtures.
6. **Non-blocking, applied — the `enumerate()` comment was ahead of the code.** It previously implied `argv[0]` was "otherwise skipped," when it is only excluded from the two containment checks and still fully participates in elevation and secret-pattern scanning. Reworded.

**Method note recorded for future reuse of ablation on this module, per the reviewer's own observation:** ablation proves a rule is *reachable* (deleting it changes an outcome); it does not prove a rule is *not evadable* by an input shape nobody wrote a fixture for. `is_remote_mutating` was both load-bearing *and* wrong at the same time — the fixture that made it load-bearing and the input that defeated it were different inputs. `remote_mutating_scan_is_not_defeated_by_a_flag_before_the_verb` is kept as a distinct test from the ablation-style ones for exactly this reason, not merged into the corpus table.

**Flagged for PR-021-D/E, not resolved in this slice — the classifier/proposal `cwd` trust boundary.** `classify` takes `cwd` as a parameter; `CommandProposal` carries its own adapter-supplied `cwd`. Neither PR-021-B nor PR-021-C is wrong to have left this alone (B correctly declined project-root containment as out of scope for a protocol decoder; C correctly takes paths as given, since a pure classifier has no independent way to know the "true" cwd) — but if the coordinator (E) passes the proposal's `cwd` to `classify` unchecked, an adapter can choose the frame its own command is judged in, and `cwd = /` would make every absolute path argument resolve as "inside the root." This must be owned explicitly by PR-021-D or PR-021-E, and the decision recorded there, not left to fall between two individually-correct scope boundaries.

### PR-021-D — Sideband channel

**Module:** `crates/tekstide-core/src/approval/channel.rs` (+ `approval/tests/channel.rs`). Path resolution (`ApprovalChannelPathRequest`/`ApprovalChannelDirectory`/`ApprovalChannelPathResolver`), token generation, and `ApprovalChannelEndpoint` (bind, accept, send, lifecycle).

**Impersonation resistance — two independent, deliberately redundant layers, both exercised with real evidence, not asserted:**

1. **Peer credentials via `SO_PEERCRED`.** The connecting process's UID is read via `libc::getsockopt(SOL_SOCKET, SO_PEERCRED, ...)` on the raw socket fd — kernel-verified at `connect()` time, not something the connecting process can influence by anything it sends. Rejects a different Unix user account outright.
2. **The per-run capability token.** Generated fresh on every `bind()` (two concatenated UUIDv4s via the already-depended-on `uuid` crate — reused rather than adding a `rand`/`getrandom` dependency solely for this — for a comfortable margin beyond a single UUIDv4's ~122 bits), compared against every incoming proposal's token. This is the layer that matters day to day: same-user-but-not-my-adapter is the realistic case on a normal desktop, and peer credentials alone cannot distinguish it.

**Real cross-process test, not a same-process simulation.** `cross_process_impersonation_with_wrong_token_is_rejected` spawns an actual separate `python3` process (sharing this test process's UID — so the peer-credential layer alone would not stop it) that connects to the real socket and submits a proposal with a wrong token. The Rust side's `accept_proposal()` correctly returns `TokenMismatch`. This is deliberately a genuinely separate OS process, not a thread in the test binary, since the property being demonstrated (token-checking catches what peer-credentials cannot) specifically requires two different processes under the same UID.

**Peer-UID mismatch itself is not exercised — could not evaluate, stated explicitly rather than left silent.** Testing "a different Unix user is rejected" would need a second real user account (or root, to change credentials), neither of which is available in this environment. The code path (`peer_uid(&stream) != self.owner_uid` → reject) is straightforward and mirrors the token-comparison path already tested, but this is recorded as an untested path, not implied to be covered by the token tests above.

**Fail closed without a dialog.** `accept_proposal()` never constructs anything a dialog could render before both authentication layers pass — a rejected connection is simply dropped, with a bounded, content-free `ApprovalChannelErrorReason` (no captured token, no captured proposal content) as the only diagnostic. This matches the RFC's fail-closed matrix entry for an invalid/absent token, and the reasoning in response 111 that a rejection path which renders a dialog is itself an attack surface.

**Path validation mirrors `audit::path`'s *resolver* shape — but response 112 found the original version of this slice had not carried over the part of the discipline that matters most.** `ApprovalChannelPathResolver` mirrors `AuditPathResolver` structurally: absolute-path requirement, canonicalization, symlink rejection via `fs::symlink_metadata`, and mutual project-root/state-root containment checks. What the first version of this slice did **not** carry over was `audit::path`'s `validate_before_open()` — a deliberate re-validation immediately before use, precisely because resolve-time checks decay. See the response-112 Defect 1 write-up below for the real, empirically-demonstrated consequence of that gap, and the fix (which goes further than a re-validation call: an `O_NOFOLLOW`-opened directory fd, closing the race rather than narrowing it). Tested directly: a symlinked `approval` directory is rejected at resolve time (`ChannelPathIsSymlink`), a project root containing the state root is rejected (`ProjectContainsChannelState`), **and** a symlink swap performed *after* resolve but *before* bind is now also rejected (`symlink_swap_between_resolve_and_bind_is_rejected`) — the case the original claim did not actually cover.

**Lifecycle: created before use, destroyed via `Drop`, recovers from a stale socket.** `bind()` creates the `approval/` directory (mode `0700`) and the socket file (mode `0600`, set explicitly after `bind()` regardless of umask) before anything connects. `Drop` removes the socket file — tested directly (`dropping_the_endpoint_removes_the_socket_file`). A leftover socket file from an ungraceful prior termination (no listener behind it) is detected by attempting a connect (refused ⇒ stale ⇒ safe to clear) rather than blindly unlinking whatever is at the path; a *live* conflicting listener is left untouched. Tested with a **real** stale socket: a raw `std::os::unix::net::UnixListener` bound at the same path and properly dropped (closing its fd while leaving the file, matching what an actual crash leaves behind) — not a simulated placeholder.

**Wire framing:** a 4-byte big-endian length prefix followed by JSON (via the already-depended-on `serde`/`serde_json`, no new dependency), decoded into typed primitives and then run through `CommandProposal::decode`/`CommandDecision`'s own validation from PR-021-B — the channel does not re-implement or duplicate that validation. A declared length beyond `MAX_MESSAGE_FRAME_BYTES` (2 MiB, chosen with headroom above `MAX_ARGV_TOTAL_LEN`) is rejected **before** attempting to read that many bytes — tested directly by sending a `u32::MAX` length prefix and confirming immediate rejection rather than the endpoint blocking forever waiting for data that will never arrive.

**A real, self-discovered test-isolation bug, fixed and disclosed rather than quietly patched over:** an early version of the test suite passed in isolation (`cargo test approval::tests::channel`) but intermittently failed under the full workspace suite. Root cause: the temp-directory helper's uniqueness counter restarted at 0 on every fresh test-binary invocation, and a symlink-path length fix (see below) had dropped the process id from the directory name, so a second test run could collide with a first run's leftover (never cleaned up) directories — a stale directory from a previous run's "symlink" test occupying the exact path a new run's "project-root-containment" test expected to be empty. Fixed by reintroducing the process id into the temp-directory name (short enough to not reintroduce the `SUN_LEN` issue below). Verified fixed by running the full `tekstide-core` suite twice in immediate succession afterward.

**A second, related, real discovery during test-writing:** the very first version of these tests used long, descriptive temp-directory names (embedding the test name, PID, and a full generated `AgentRunId`). Several tests failed with `path must be shorter than SUN_LEN` — a genuine Unix domain socket path-length limit (~108 bytes on Linux), not a bug in the channel code. This is exactly the known limitation already documented in `channel.rs`'s module doc (`socket_path`'s doc comment) for unusually long *state-root* paths — the test fixtures had simply reproduced that limitation themselves through verbose naming. Fixed by shortening the test fixture names; the underlying limitation for real, unusually deep state-root paths remains and is recorded in Known Limitations, not solved (solving it well would need a hashing dependency this crate does not otherwise need).

**What this slice deliberately does not decide, flagged for PR-021-E:** whether `CommandProposal.cwd()` reflects the adapter's *true* working directory, as opposed to whatever value it declares. This is the cwd-trust-boundary gap response 111 (PR-021-C re-review) identified as falling between two individually-correct scope decisions in B and C. This module authenticates *who* is connecting, not what a validated message's fields *mean* relative to the actual `AgentRun`/`ProjectSession` state — that synthesis is the coordinator's job in PR-021-E, which has access to state this module deliberately does not depend on.

**Response 112 follow-ups (2026-07-29), all applied — three real, empirically-reproduced defects, not theoretical concerns.** The reviewer confirmed the hard gate first: *"impersonation resistance is established... the defects below are in the surrounding machinery — path handling, lifecycle, blocking behaviour — not in the authentication design."*

**Defect 1 — the socket could be placed outside the state root via a symlink swap between `resolve()` and `bind()`.** `resolve()` checked the channel directory was not a symlink; `bind()` never re-checked before actually binding, so a same-user process that replaced `<state_root>/approval` with a symlink in that window got the endpoint bound (and `chmod`'d to `0700`) inside its own target directory instead. The reviewer's probe reproduced this directly. **Fix: goes beyond a re-validation call, to closing the race rather than narrowing it.** `bind()` now opens the channel directory with `O_NOFOLLOW` via `libc::open` (`open_dir_no_follow`), which fails outright if the directory is a symlink *at that exact moment* — and every subsequent operation (the stale-socket check, the actual `UnixListener::bind`, the permission `chmod`) goes through a `/proc/self/fd/<fd>/<filename>` path that resolves via that already-verified fd, not by re-resolving the directory's pathname a second time. A pathname-based swap after this point has nothing left to redirect. New test: `symlink_swap_between_resolve_and_bind_is_rejected` reproduces the reviewer's exact probe (resolve, then swap, then bind) and confirms refusal.

**Defect 2 — `bind()` could panic on a relative `$TMPDIR`.** The token self-check validated a freshly-generated token by round-tripping it through `CommandProposal::decode` with a placeholder `cwd` of `std::env::temp_dir()` — which returns `$TMPDIR` unvalidated, and a relative value fails `decode`'s absolute-path check, turning an `.expect()` into a panic inside a security boundary. The reviewer named the deeper issue precisely: *"token validation is coupled to the validity of four unrelated fields and to process environment state."* **Fix:** `protocol.rs`'s `validate_token` (previously private, the single implementation `CommandProposal::decode` already used internally) is now `pub(crate)`, and `approval::channel` calls it directly — no `CommandProposal` construction, no `cwd`, no environment dependency, no possible panic. `RunCapabilityToken` remains unconstructable from outside `approval`, per the reviewer's explicit instruction to preserve that property while removing the workaround that had grown around it.

**Defect 3 — a silent same-user peer could wedge the channel indefinitely.** `accept_proposal` blocked in `read_frame` with no timeout; a connected peer that sent nothing (or a partial frame) held the call — and every connection after it, including the real adapter's — forever. The reviewer's framing matters more than the mechanism: *"fail-closed is not the end of the analysis... a wedged channel means the adapter's commands never run and the user gets no explanation. The pressure that creates is the user disabling approval or running the command by hand"* — the third time this exact argument (over-rejection in 109, over-escalation in 110, now blocking-without-recourse in 112) has applied to a different mechanism. **Fix:** a read timeout (`PROPOSAL_READ_TIMEOUT`, 30s — deliberately unrelated to and much shorter than the RFC's unbounded "no approval timeout" policy, which governs human decision time *after* a proposal is already received, not how long an adapter has to finish transmitting one) is set on the accepted stream before the first read; timeout surfaces as a new, distinguished `ReadTimedOut` reason. New test (`silent_peer_triggers_a_read_timeout_rather_than_blocking_forever`) uses a test-only timeout override (`set_read_timeout_for_test`) so the test itself takes a bounded fraction of a second rather than 30 real ones, and asserts both the correct error and that `accept_proposal` actually returned promptly rather than merely eventually.

**Q3 (stale-socket heuristic) — a real problem, confirmed and fixed.** `clear_stale_socket` treated any `ECONNREFUSED` from a connect attempt as "stale socket, safe to unlink" — but connecting to a *regular file* also yields `ECONNREFUSED`, so any non-socket file occupying the target path was silently deleted. Fix: check `fs::symlink_metadata(..).file_type().is_socket()` first and refuse anything else outright, before ever attempting a connect. New test (`stale_socket_clearing_refuses_a_non_socket_file`) creates a plain regular file at the socket path and confirms `bind()` refuses and the file is left untouched (existence and contents both re-checked).

**Recommended fixes, all applied:**

- **Token checked immediately after JSON parsing, before full `CommandProposal::decode`** — an unauthenticated peer's bytes now reach strictly less code, and `TokenMismatch` is the accurate answer to "why was this rejected" rather than whatever `decode` happened to reject first.
- **Constant-time token comparison.** `RunCapabilityToken`'s derived `PartialEq` (byte-wise `String` comparison, short-circuiting at the first differing byte) is replaced with a manual, three-line constant-time comparison. The reviewer's framing is recorded verbatim because it is the right way to think about this class of fix: *"we measured the noise floor and judged it unexploitable" is a weaker thing to write in a closeout than "it does not vary."*
- **`#[serde(deny_unknown_fields)]`** added to `WireCommandProposal` — an unrecognized field now fails closed the same way an unknown protocol version does, rather than being silently ignored.
- **`MAX_MESSAGE_FRAME_BYTES` raised from 2 MiB to 8 MiB**, reconciling the frame bound with JSON string-escaping expansion (up to sixfold, `\u00XX`) of `MAX_ARGV_TOTAL_LEN` (1 MiB) — a legitimate proposal near the argv ceiling with heavily-escaped content was at risk of being unframeable at the old bound.

**Q1 (is `SO_PEERCRED` worth it given it was untested?) — answered, and the untested gap is now narrowed rather than left as-is.** The reviewer's answer: keep it, and the premise was wrong — the two layers "do not overlap; they cover different failures" (the token's security rests entirely on secrecy, and `/proc/<pid>/environ` is readable by the same user, so a same-user attacker who can read the adapter's environment already has the token and peer-cred is what still stands between a *cross-user* attacker and the endpoint in that scenario). Per the reviewer's suggested approach, a test-only setter (`set_owner_uid_for_test`) now lets `peer_credential_mismatch_is_rejected` exercise the comparison itself (`peer_uid != self.owner_uid`) end-to-end by varying `owner_uid` to a deliberately wrong value rather than the peer's real UID — which converts "the comparison is untested" into "the comparison is tested, and the syscall's correctness is the documented assumption," a meaningfully smaller residual claim. What genuinely remains unverified (stated precisely, per the reviewer's instruction): that `getsockopt(SO_PEERCRED)` itself reads the kernel's value correctly for a *different real user* — nothing short of a second real account or root can verify that.

Recorded below with the reviewer's own framing kept intact, since it is the more useful lesson than either fix in isolation.**

**Required 1 — the `/proc/self/fd` fix traded a loud early failure for a silent late one.** Response 112's fix bound through a short `/proc/self/fd/<fd>/<filename>` path rather than the real, potentially long `socket_path`. The reviewer's probe: at a 266-byte state root, the real socket path (327 bytes) exceeded `sun_path`'s capacity, yet `bind()` succeeded — because the *bind* path was short — while a real adapter's `connect()`, which must use the real path, failed with `"path must be shorter than SUN_LEN"`. The result presents identically to the wedge response 112 Defect 3 fixed (adapter never connects), but for an unrelated reason, and is harder to diagnose than the original loud `bind()`-time failure it replaced. **Fix:** `bind()` now checks `directory.socket_path(agent_run_id).as_os_str().len()` against a new `max_socket_path_len()` (computed from `size_of::<libc::sockaddr_un>() - size_of::<libc::sa_family_t>() - 1`, no hashing dependency needed) as its very first action, before any fd is opened, and returns a new distinguished `ApprovalChannelErrorReason::SocketPathTooLong` if it is exceeded. New test: `bind_rejects_a_state_root_deep_enough_to_exceed_sun_path` constructs a real deep state root (six 40-character path components), confirms as a precondition that the real socket path actually exceeds 107 bytes, and asserts the distinguished error. Ablation-verified: temporarily disabling the length check (`if false && ...`) makes the same test fail with `bind()` succeeding instead, confirming the check is load-bearing, then restored. The stale doc comments this fix corrects are addressed below (this Known Limitations entry, and `socket_path`'s doc comment in `channel.rs`).

**Required 2 — the ancestor-swap race, not closed by the previous fix, only narrowed.** The response-112 commit message claimed the symlink-swap fix "closed the race rather than narrowing it." The reviewer's probe showed this was false: `O_NOFOLLOW` on `open_dir_no_follow(directory.channel_dir())` protects only the **final** path component (`approval`) — replacing the **state root itself** with a symlink between `resolve()` and `bind()` still placed the socket outside the state root, one directory higher than the race response 112 closed. The reviewer judged the practical severity low (a same-user attacker already has easier options — reading `/proc/<pid>/environ` for the token, `ptrace`, replacing `PATH` binaries) but required the fix anyway, for claim accuracy rather than threat severity, quoting response 110's own standard back: *"a checked box means evidence exists."* Took the reviewer's explicitly preferred fix rather than the alternative (documenting the residual gap and unmarking the checklist line): **`ApprovalChannelPathResolver::resolve()` now opens `state_root` itself with `O_NOFOLLOW` once, immediately after canonicalizing it, and stores the resulting `OwnedFd` (wrapped in `Arc`, since `OwnedFd` is not `Clone` and a directory value may be reused across multiple `bind()` calls) in `ApprovalChannelDirectory` as `state_root_fd`.** `bind()` no longer calls `open_dir_no_follow(directory.channel_dir())` (which re-resolved `state_root`'s pathname every time); it instead calls a new `mkdirat_if_missing`/`openat_dir_no_follow` pair, both relative to `state_root_fd`, to create and open the `approval` subdirectory. Because the fd was opened once and never re-resolves its own pathname, no swap of `state_root` — at any point after `resolve()` returns, no matter how long a caller waits before calling `bind()` — can redirect where the channel directory actually opens. New test: `ancestor_symlink_swap_of_the_state_root_itself_is_rejected` reproduces the reviewer's exact probe (resolve, then replace `state_root` itself with a symlink to an attacker-controlled directory, then bind) and confirms rejection, plus confirms no socket was created inside the symlink target. Ablation-verified: temporarily reverting `bind()` to the old `open_dir_no_follow(directory.channel_dir())` pattern (without `state_root_fd`) made this exact test fail, confirming it is genuinely load-bearing and not merely re-testing the already-fixed final-component case, then restored to the real fix.

**Required 3 — `PROPOSAL_READ_TIMEOUT` shortened from 30s to 5s, per Q2's answer (see below).**

**Required 4 — the `/proc` dependency is now a documented assumption with a distinguished failure mode.** Response 112's fix introduced a hard dependency on `/proc/self/fd` being mounted and functional — true for every desktop Linux target Tekstide runs on, but not universal (some minimal containers and hardened configurations omit it). Previously, a failure here would have surfaced as a bare `io::Error` indistinguishable from any other bind failure. **Fix:** a new `verify_proc_fd_magic_path_available` checks that `/proc/self/fd/<fd>` resolves for the directory fd `bind()` just opened itself — isolating the check to the one thing it is actually about, rather than to whatever operation happens to use the magic path next — and returns a new distinguished `ApprovalChannelErrorReason::ProcMagicPathUnavailable` on failure. Documented directly in the module: `magic_fd_path`'s doc comment now states explicitly (per the reviewer's Q1 item 3) that the short bind path is *incidental* to closing the TOCTOU race, not a feature that lifts the `sun_path` limit — specifically so a future reader does not remove the Required-1 length check on the mistaken theory that the short path made it unnecessary.

**Q1 (is `/proc/self/fd` the right mechanism?) — confirmed sound, with the three caveats above now addressed rather than left implicit.** The reviewer confirmed the reasoning for rejecting `fchdir` (process-wide CWD mutation would be a worse bug in a future multithreaded GUI process than the one being fixed) was correct, and flagged three things to be aware of, each closed above: the hard `/proc` dependency (Required 4), the fact that pinning only the final component was insufficient (Required 2), and that the magic path's shortness incidentally caused Required 1 rather than being a deliberate feature (documented in `magic_fd_path`).

**Q2 (is 30 seconds right?) — no, shortened to 5, and concurrent connection handling promoted from an open question to required E1 scope.** The reviewer's point: the timeout's exact value matters less than what a single-threaded, one-connection-at-a-time accept loop means for an attacker who loops connect-and-stall — they still occupy the one slot repeatedly, just in shorter increments, so the timeout converts unbounded blocking into bounded-but-repeatable blocking, not into an actual fix for the underlying denial. `PROPOSAL_READ_TIMEOUT` is now `Duration::from_secs(5)` (a local adapter writing one already-composed frame needs milliseconds even on a loaded machine), remains deliberately not configurable (a user-tunable timeout on a security control invites setting it to something unhelpful), and concurrent connection handling — response 112 had framed this as an open question for E — is now recorded as required PR-021-E1 scope, not optional.

**Q3 (anything to reconsider in the E1/E2 split?) — three adjustments, all recorded as required E1 scope, not reconsidered as open questions:** (1) token delivery through the environment allowlist moves into E1 — `bind()` currently returns the raw token and nothing injects it, and the reviewer's framing is that this is itself a security property (the token must reach the adapter *only* by that route, and must never land in an audit record, a log, or a crash dump), not coordination plumbing, so it belongs with the other security decisions rather than deferred as launch-path wiring; (2) concurrent connection handling, per Q2; (3) the `cwd`-verification test must assert the *reclassification* direction, not only rejection — a proposal claiming `cwd = /` must not be able to make an absolute path look project-internal, and that must be a fixture, not a sentence, written before the coordinator exists (same discipline as PR-021-C's "unclassifiable is `High`" test).

### PR-021-E1 — Trusted-context coordinator (verified cwd, single-use decisions, concurrent connections, token delivery)

**Module:** `crates/tekstide-core/src/approval/coordinator.rs` (new, + `approval/tests/coordinator.rs`), plus additions to `approval/channel.rs` (`serve_concurrently`, `inject_token_into_environment`). Scope per response 113's developer handoff, items 5–8; PR-021-E2 (audit-family wiring, the `CommandDecision` round trip over the channel, edit-and-approve reclassification) is explicitly not this slice — see the E1/E2 split confirmed in response 113 Q3.

**Verified `cwd` (item 7) — enforced structurally, not by convention.** `ApprovalCoordinator::receive_proposal` takes `verified_cwd: &Path` and `project_root: &Path` as separate, caller-supplied parameters; there is no parameter, anywhere in this module's public API, that accepts `CommandProposal::cwd()`'s value. `risk::classify` is called only with the caller-supplied values — `proposal.cwd()` is never read. Response 111 (PR-021-C re-review) and response 113 both flagged this as a gap between two individually-correct scope decisions (B declined path containment as out-of-scope for a protocol decoder; C takes paths as given); this slice is what finally has access to real, already-authenticated context to close it.

**The `cwd = "/"` fixture, written as a differential test rather than a sentence, per response 113 Q3 item 3.** `a_claimed_cwd_of_root_cannot_make_an_external_path_look_project_internal` first demonstrates the exploit *directly*: calling `risk::classify` with the proposal's own claimed `cwd()` used as the project root (the exact misuse the fixture guards against) does **not** escalate an external path referencing `/etc/shadow` — proving the vulnerability is real if a coordinator implementation were ever careless about which value becomes the containment boundary. It then calls the real `ApprovalCoordinator::receive_proposal` with the correct, separately-sourced `project_root`, and confirms the same proposal **does** escalate (`RiskLevel::High` or above). A companion test, `a_claimed_cwd_of_root_does_not_cause_a_genuinely_internal_path_to_escalate`, proves the other direction: a genuinely internal path is not wrongly escalated just because the proposal also claims a suspicious `cwd` — without this, "ignore the claimed cwd" could be trivially (and uselessly) satisfied by a coordinator that just always escalates.

**Proposal-id uniqueness and single-use decisions (item 8), written first, per the reviewer's instruction — the same discipline as PR-021-C's "unclassifiable is `High`" test.** `ApprovalCoordinator` keys its in-memory bookkeeping by `(AgentRunId, ProposalId)`. **This slice's first version returned the stored, possibly-already-decided request on a repeat** (`ReceiveOutcome::Duplicate(ApprovalRequest)`) — response 114 Required 1 found this let an approval granted for one argv be read as authorization for a resubmission under the same id with completely different, far riskier argv (a real laundering vulnerability, the most serious finding in RFC-021 to date; see the response-114 write-up below). **Fixed:** a repeat now returns `ReceiveOutcome::DuplicateRejected { proposal_id }`, carrying no `ApprovalRequest` at all. `decide` returns `DecideOutcome::AlreadyDecided` (the existing terminal state, unchanged) for a repeated decide call on an already-decided proposal id — `decision_is_single_use_and_replay_is_inert` proves this by deciding `ApprovedOnce` and then replaying with `Rejected`, confirming the request still shows `ApprovedOnce`, never flips. Both dedup guards are ablation-verified: temporarily bypassing each (the duplicate check; the domain-level `Pending`-only guard, replaced with a direct field overwrite to simulate a genuinely broken implementation) made the corresponding test fail, then restored.

**Also verified: the same proposal id in a different `AgentRun` is not a duplicate** (`the_same_proposal_id_in_a_different_agent_run_is_not_a_duplicate`), and **the classifier never consumes `UntrustedEffectsHint`** (`the_coordinator_never_lets_the_declared_effects_hint_affect_classification`) — two otherwise-identical proposals differing only in `declared_effects` (one claiming "this only reads files, it is completely safe" over an `rm -rf` invocation) classify identically (`Destructive`), proving the coordinator — the piece that actually wires `CommandProposal` to `risk::classify` — never lets the adapter's self-declared safety claim influence the outcome. This was one of my own E1 items from review-request 113, confirmed valid by the reviewer to keep.

**Design choice, disclosed:** `decide()` does not yet handle edit-and-approve reclassification (`implementation-handoff.md` §7 — re-running the classifier on edited argv). This is deferred to PR-021-E2 along with the rest of the decision round trip; `decide()`'s signature deliberately stays simple (decision only, no edited argv) for this slice rather than half-building reclassification without the audit wiring it needs to mean anything.

**Concurrent connection handling (item 5, promoted from an open PR-021-E question to required E1 scope per response 113 Q2).** `ApprovalChannelEndpoint::accept_proposal` still authenticates one connection at a time (preserved, unchanged, so none of the 18 existing channel tests needed to change). A new `serve_concurrently(self: Arc<Self>) -> mpsc::Receiver<...>` spawns one thread per accepted connection so `listener.accept()` is called again immediately rather than after the previous connection finishes authenticating (which could take up to `PROPOSAL_READ_TIMEOUT`). `authenticate_and_read` is the shared implementation both `accept_proposal` and `serve_concurrently`'s per-connection threads call, so there is exactly one authentication code path, not two to keep in sync.

**Real, not simulated, evidence for the concurrency fix.** `serve_concurrently_accepts_a_second_connection_while_the_first_stalls` spawns a real slow peer that connects and holds its connection open for 600ms sending nothing, then (after a 100ms head start) spawns a real well-behaved peer that sends a valid proposal frame immediately, and asserts the well-behaved peer's result arrives via the channel within 400ms — proving it was not queued behind the stalling connection. Ablation-verified: temporarily processing connections synchronously in the accept loop (the pre-fix shape) made this exact test fail with a timeout, then restored. Full suite re-run three times in succession to confirm this timing-sensitive test is not flaky (stable at 449 tests each run).

**Token delivery through the environment allowlist (item 6, promoted from launch-path wiring to a security decision this module must own, per response 113 Q3 item 1).** A new `APPROVAL_TOKEN_ENV_VAR` constant and `inject_token_into_environment(command, token)` function in `channel.rs` are now the single sanctioned choke point for delivering a `RunCapabilityToken` to a child process's environment. `inject_token_into_environment_sets_the_sanctioned_variable_on_a_real_child_process` verifies this against a real, separately spawned `sh` child process reading back its own environment — not merely asserting the `Command` builder was called.

The existing known-limitation fixture, `a_cwd_mismatch_is_not_yet_compared_or_audited_known_limitation`, is renamed and converted to `a_cwd_mismatch_is_compared_and_recorded_as_a_best_effort_audit_anomaly`, asserting presence of the anomaly record in a real, queried store rather than documenting its absence; a companion `a_matching_cwd_produces_no_mismatch_anomaly` proves the converse (an agreeing claim produces no anomaly, so the signal stays meaningful rather than firing on every proposal). Ablation-verified: temporarily forcing `cwd_mismatch_audit = None` unconditionally made the presence fixture fail (`left: None, right: Some(Persisted)`), then restored.

## Known Limitations

- Approval applies only to adapter-submitted proposals. An AI CLI that does not implement the contract is unaffected, and `Plain`/`Supervised` runs have no approval path by design.
- No pattern-based or always-allow rules. Every proposal requires a decision, which may prove noisy in practice; the remedy is a reviewed pattern language in a later RFC, not a silent threshold.
- No approval timeout. A pending proposal blocks the adapter indefinitely.
- The exact command is held in memory for display but never persisted, so durable audit cannot answer "what command was approved" — only that an approval occurred, at what risk level, for which run.
- **The risk classifier's path containment is lexical, not canonical (PR-021-C, response 110 Recommended 3).** An in-root symlink whose target points outside the project root is not detected by `approval::risk::classify` — e.g. `cat link/secret` where `link` resolves outside the root classifies the same as any ordinary in-root path. Detecting that is RFC-011/RFC-012's job, enforced at the point of actual file access; the classifier intentionally stays a pure, filesystem-free function so it can classify proposals referencing paths that do not exist yet.
- **Wrapper indirection is only partially recognized (PR-021-C).** `env`, `nice`, `timeout`, `xargs`, `stdbuf`, and `nohup` are individually recognized as opaque wrappers (`High`/`OpaqueWrapper`), and a shell interpreter as `argv[0]` is always `High`, but none of these are unwrapped to classify the real command underneath — `env git status` classifies `High` rather than the `Low` a direct `git status` would get. Confirmed by response 110 to be over- rather than under-classification, and deferred deliberately rather than building unreviewed unwrapping under time pressure.
- **`git stash clear`/`git stash drop` classify `High` (`RiskReason::WorkingTreeDiscard`), not `Destructive`** — a deliberate, smaller severity than discarding tracked working-tree changes directly, since stashes are already a secondary safety net. Confirmed by response 111 as the right severity; the fix in that response was giving the decision a named reason and fixtures, not changing the level.
- Attached *short* command-line options (`-o/etc/x`) are not resolved as path candidates; only the `--long-option=value` attached form is, and only when the entry starts with `-` (PR-021-C, response 110 Mandatory 2, refined by response 111 non-blocking-2).
- **`git push --force` and `git push --force-with-lease` classify identically (both `Destructive`/`RemoteHistoryRewrite`), despite `--force-with-lease` being genuinely safer** (it refuses to overwrite a remote ref that has moved since the last fetch). Response 111 explicitly endorsed skipping this distinction as a refinement, not a defect.
- **Resolved in PR-021-E1: the classifier/proposal `cwd` trust boundary flagged after PR-021-D (response 111) is now closed.** `ApprovalCoordinator::receive_proposal` takes `verified_cwd`/`project_root` as separate, caller-supplied parameters and never reads `CommandProposal::cwd()`; the `cwd = "/"` exploit is reproduced and shown closed by a differential fixture (see PR-021-E1 write-up). What is *not* yet resolved: nothing in this crate yet supplies `verified_cwd`/`project_root` from real `AgentRun`/`ProjectSession` state to a live coordinator instance — that wiring (whatever eventually calls `receive_proposal` for a real, running `AgentRun`) is PR-021-E2 scope, since it requires the audit/dispatch plumbing this slice deliberately does not build.
- **Resolved in PR-021-E2 (response 114 Q3): `receive_proposal`'s `verified_cwd` parameter is now `&VerifiedCwd`, not `&Path`.** A new `agent::VerifiedCwd` newtype has no public constructor accepting an arbitrary path — the only way to obtain one is via `AgentRunLaunchValidator::validate` succeeding. Passing `proposal.cwd()` as `verified_cwd` no longer typechecks at all; the type signature is now the actual enforcement mechanism, not a comment asking callers to be careful.
- **Resolved in PR-021-E2 response 116 (Required 2): a proposal's claimed `cwd` differing from `verified_cwd` is now compared and recorded as a best-effort `command_cwd_mismatch` audit anomaly.** Converted from a deferred Known Limitation (response 114 Recommended 3) to required, since PR-021-E2 was the last implementation slice. Never trusted, never used for classification — the comparison happens strictly after classification and storage have already used `verified_cwd` alone; this is observability only. See the PR-021-E2 write-up's Response 116 follow-ups, item 2.
- **Resolved in PR-021-E2 (response 115 Q2): `RiskReason`s now live on `domain::ApprovalRequest.risk_reasons`, next to `risk_level`**, not only on the transient `ReceiveOutcome` — moved into `domain::approval` (where `RiskLevel` already lived), with `approval::risk` re-exporting rather than defining `RiskReason` itself. A stored `ApprovalRequest` alone can now answer "why" a decision was reached, without needing the original `ReceiveOutcome` still in hand.
- **`SO_PEERCRED`'s correctness for an actually different real user is unverified (PR-021-D, narrowed per response 112 Q1).** The comparison (`peer_uid(&stream) != self.owner_uid`) is now tested (`peer_credential_mismatch_is_rejected`, via a test-only `owner_uid` override), which converts the residual claim from "the comparison is untested" to the smaller: whether `getsockopt(SO_PEERCRED)` itself reads the kernel's value correctly for a genuinely different real user is unverified, since that would need a second real user account or root access, neither available in this environment.
- **Resolved in PR-021-E1 (response 113 Q2 denial), and corrected in response 114 (Required 3/4): concurrent connection handling.** A silent, same-user peer can still occupy the connection *it holds* for up to `PROPOSAL_READ_TIMEOUT` (5s), but `ApprovalChannelEndpoint::serve_concurrently` spawns one authentication thread per accepted connection (bounded by `MAX_CONCURRENT_CONNECTIONS = 32`, response 114 Required 4 — the first version of this fix had no cap, letting the same-user peer exhaust threads instead of merely one slot), so a stalling peer no longer delays `listener.accept()` from being called again. The accept loop holds only a `Weak<Self>` and is stopped via the `ServeShutdown` handle `serve_concurrently` returns (response 114 Required 3 — the first version captured a strong `Arc` in the loop itself, which meant `Drop` could never run and the socket file was never removed no matter what the caller did). `accept_proposal` (one-at-a-time) is preserved unchanged for existing callers/tests; `serve_concurrently` is the new, additional entry point.
- **New in PR-021-E1: token delivery through the environment allowlist has exactly one correct call site (`inject_token_into_environment`), but no production caller yet.** No code path in `runtime::terminal` spawns a distinct "adapter" process as opposed to a plain interactive shell — `spawn_shell` always uses a fixed, hard-coded environment, and `TerminalEnvironmentPolicy::ExplicitAllowlist` is not yet applied by the Linux runtime. Building that adapter-spawn pathway is out of this slice's scope (it touches `runtime::terminal`, not `approval`) and is flagged for the next review rather than built unreviewed.
- **Resolved in PR-021-E2: edit-and-approve re-classification (`implementation-handoff.md` §7).** `ApprovalCoordinator::decide_with_edited_argv` re-runs the classifier on the edited argv and updates `display_command`/`risk_level`/`risk_reasons` before recording the decision. **Corrected by response 116 (Required 1): the initial version reclassified before *applying* the decision but after *authorizing* it, so the durable `Authorized` record itself still described the proposed command's risk, not the edited one — fixed by moving reclassification ahead of the authorization call; see the PR-021-E2 write-up's Response 116 follow-ups, item 1.** **`RunCapabilityToken::as_str()`'s `pub(crate)` visibility (response 114 Recommended 1) means no downstream crate can log the raw token — recorded here as a still-relevant reminder, not a new limitation.**
- **Still open after PR-021-E2, unchanged from PR-021-E1: no adapter-spawn pathway exists in `runtime::terminal`**, so `inject_token_into_environment` has no production caller, and neither does `ApprovalCoordinator` itself — this slice remains fully headless. Per response 114 Q1: RFC-021 will close with no production caller, and PR-021-F's honesty-checklist wording must say so plainly.
- **Unix socket path length (`sun_path`, ~108 bytes on Linux) is now pre-validated at `bind()` (PR-021-D, response 113 Required 1).** `bind()` checks the real `socket_path` (not the short `/proc/self/fd`-relative path it actually binds through) against `sun_path`'s capacity before doing anything else, and returns a distinguished `ApprovalChannelErrorReason::SocketPathTooLong` rather than a bare `io::Error`. This closes a regression response 112's `/proc/self/fd` fix introduced: binding through the short fd-relative path no longer failed at `bind()` on a deep real state root, so the failure moved silently to the adapter's later `connect()` call instead, against an endpoint that otherwise looked healthy. Not worked around with a shortened/hashed filename, since doing that well would need a hashing dependency this crate does not otherwise need for anything else — the length is validated, not avoided.
- **This module's fd-relative binding mechanism depends on `/proc/self/fd` being mounted and functional (PR-021-D, response 113 Q1/Required 4).** True for every desktop Linux target Tekstide runs on; not universal (some minimal containers and hardened configurations omit it). `bind()` checks this explicitly against the fd it just opened itself and returns a distinguished `ApprovalChannelErrorReason::ProcMagicPathUnavailable` rather than a bare `io::Error` if the check fails.

## What Tekstide may claim about command approval

This is the statement PR-021-F exists to produce. It is binding on the README, release notes, and any future marketing or documentation text. **Each paragraph is here because a shorter version of it would be false.**

**Implemented.** Tekstide has a command-approval model: a versioned sideband protocol over a per-AgentRun Unix domain socket under the state root; two-layer peer authentication (kernel-verified `SO_PEERCRED` plus a per-`bind()` capability token compared in constant time); a structural risk classifier over argv and cwd; a coordinator that assigns single-use decisions to unique proposal ids, re-classifies edited argv before authorising it, and writes the `command_approval` audit family through `AuditCoordinator` with authorisation preceding application.

**Not reachable.** No user can encounter any of it. There is no adapter-spawn pathway — `runtime::terminal::spawn_shell` launches a plain interactive shell with a fixed environment, and `TerminalEnvironmentPolicy::ExplicitAllowlist` is rejected as unsupported before a process starts — so `inject_token_into_environment` has no production caller and neither does `ApprovalCoordinator`. There is no dialog, because there is no GUI. **Every property above is implemented and tested; none of it is wired to anything a user can reach.**

**Cooperative, not enforced.** Approval works only if the adapter asks. Tekstide does not intercept process execution, does not use `ptrace`, `seccomp`, `LD_PRELOAD`, or any OS-level mechanism — verified absent by grep across the workspace — and has no execution path of its own to withhold. An adapter that ignores a `Rejected` decision, or that never submits a proposal in the first place, runs its command unimpeded. **Nothing in this RFC prevents that, and no wording may imply otherwise.**

**Therefore, the sentence that must not be written** is any variant of "Tekstide approves commands", "Tekstide controls what the AI can run", or "commands require approval". The accurate forms are: *"Tekstide implements a command-approval protocol that a cooperating AI CLI adapter can use"*, and, until the adapter-spawn pathway and dialog exist, *"command approval is not yet available to users."*

**On the audit trail specifically.** The `command_approval` family is wired and its records are correct — verified by reviewer probe against a real store, including that no argv, cwd, intent, effects hint, proposal id, or display text reaches the durable database. But with no production caller, it produces nothing. "Audit records command approvals" is false today; "the audit schema and producers for command approval exist and are tested" is true.

## Decisions on the RFC's open questions

**1. Ship a reference wrapper adapter, or define the contract and wait for CLI support?**

**Define the contract; do not ship a wrapper in v1.** A Tekstide-authored wrapper would be the only thing exercising the protocol, which makes it simultaneously the reference implementation and the sole test subject — and it would invite the claim that approval "works", when what worked was Tekstide talking to itself. It also creates a supply-chain surface (a process Tekstide spawns to wrap another process) for a feature whose honest description is "cooperative." Revisit if a real AI CLI implements the contract; the decision to reverse is cheap, the decision to un-ship a wrapper is not.

**2. Restrict `EditedAndApproved` for `Destructive` proposals, where editing may mask intent?**

**No restriction. Editing is re-classified, which is the stronger control.** `decide_with_edited_argv` re-runs the classifier on the edited argv and — as of response 116 Required 1 — authorises against the *edited* risk level, so an edit that turns something benign into something destructive is recorded as destructive. Blocking edit-and-approve at `Destructive` would push users toward approving the original unedited command, which is worse. The residual risk is that a user edits a `Destructive` command into a different `Destructive` command; the audit record describes what was approved, which is the property that matters.

**3. Should proposals persist across a Tekstide restart, or always be abandoned?**

**Always abandoned, and this is safe rather than merely unaddressed.** `ApprovalCoordinator`'s bookkeeping is in-memory, so a restart forgets every pending proposal and nothing executes — the failure direction is closed. Crucially, `bind()` generates a fresh token per endpoint, so an adapter holding a pre-restart token cannot authenticate afterwards either; there is no window in which a stale decision could be replayed. Persisting proposals would create exactly that window in exchange for convenience on a path that has no users. Recorded as a deliberate non-goal, not a gap.

## Verified by reviewer probe at closeout

Beyond the per-slice reviews, three closeout-specific checks:

- **No OS-level interception anywhere in the workspace.** `grep` for `ptrace`, `seccomp`, `LD_PRELOAD`, `bpf` across `crates/`: no matches.
- **No pattern-based or always-allow rules.** `grep` for `always_allow`, `AlwaysAllow`, `allowlist_pattern`, `remember_choice`, `ApproveAlways` across `approval/`: no matches.
- **No timeout can approve.** `coordinator.rs` contains no `Duration`, `Instant`, `elapsed`, `SystemTime`, or `now()`. It records `created_at` only via `ApprovalRequest::pending`, and reads no timestamp anywhere. The single timeout in the whole module is `channel.rs`'s `PROPOSAL_READ_TIMEOUT`, whose only effect is to drop a connection — it cannot produce a decision. **See required follow-up below: this is currently guaranteed by absence, and absence does not survive a future edit silently.**

## Required follow-up before RFC-021 is complete

**One item.** Add a regression test asserting that a received proposal remains `Pending` with no decision after elapsed time, and that no code path in `approval` reads a timestamp to decide. The property is real — I verified it structurally above — but "no timeout approves" is the RFC's headline fail-closed guarantee, and it is presently held by the absence of code rather than by a test that fails if someone later adds a timeout for a good-sounding reason. This is the same class as a fixture corpus that cannot fail (response 110).

Small, and it is the last thing owed on this RFC.

## Obligations carried forward

These are not RFC-021 defects; they are work this RFC's design requires of others.

1. **Adapter-spawn pathway — its own slice, needs an owner decision.** Enabling `TerminalEnvironmentPolicy::ExplicitAllowlist` changes the terminal security boundary (RFC-009/RFC-010 territory), not the approval channel. Until it lands, nothing in RFC-021 is reachable.
2. **RFC-022 inherits the dialog**, and with it: rendering `display_command` through `text_safety` (already the shared primitive — `approval::coordinator` calls it, so the dialog inherits escaping rather than reimplementing it), surfacing `risk_reasons` so a user learns *why* a command is `High`, and the fail-closed obligations still unchecked here (adapter disconnect and AgentRun termination while pending → abandoned).
3. **`Plain`/`Supervised`/`Managed` per-mode gating is unbuilt.** The checklist lines for it stay unchecked deliberately: they are vacuously true today because no run mode reaches approval at all, and a vacuous pass is not evidence of a gate. Whoever wires the adapter-spawn pathway owes the real gate.
4. **Residual limitations**, each recorded in its own place above: lexical (not canonical) path containment in the classifier; wrapper indirection not unwrapped; attached short options (`-o/path`) uncovered; `SO_PEERCRED` correctness for a genuinely different real user unverified without a second account; `/proc/self/fd` dependency for fd-relative binding; in-memory coordinator bookkeeping.
