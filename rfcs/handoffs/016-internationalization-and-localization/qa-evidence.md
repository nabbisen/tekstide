# RFC-016: Internationalization and Localization - QA Evidence

Status: Proposed — implementation in progress (PR-016-C complete and accepted; PR-016-B complete and accepted [response 122, fixes confirmed by response 123]; PR-016-D complete and accepted [response 126]; PR-016-E waits for RFC-015 per the scan-scope obligation in response 122, now also carries response 126's interpolation-guard scope note; PR-016-F last)
Date opened: 2026-07-29
Date accepted: Pending

## Scope

RFC-016 delivers the localization machinery and the text-safety rules for untrusted text rendered in trusted surfaces.

Evidence in this file must not be used to claim confusable/homoglyph protection, RTL layout mirroring, runtime locale switching, terminal-grid bidi reordering, terminal wide-cell CJK, or completed translations into any specific language — unless later reviewed implementation explicitly supports that claim.

## The security finding this RFC exists to fix

Verified 2026-07-29, before implementation:

- The RFC-009 `SecurityFilter` forwards `input(c: char)` unconditionally. Bidi controls are printable Unicode, not C0/C1, so they were never part of the accepted/inert classification.
- `tekstide-core`'s `TerminalSecurityParser` contains no bidi handling; U+202A..U+202E and U+2066..U+2069 pass through as ordinary text.
- RFC-014 C10 demonstrated the editor surface performs full Unicode bidi reordering via `cosmic-text`.

Consequence: a command string containing U+202E would render reversed in RFC-021's approval dialog — Trojan Source (CVE-2021-42574) applied to the surface whose entire purpose is showing the user exactly what will run. PR-016-C closes this.

### PR-016-B — Catalog, locale selection, fallback

**A sequencing gap found before implementation, disclosed rather than silently resolved.** `implementation-handoff.md` describes this slice as replacing a placeholder `i18n.rs` RFC-015 was to create, with an explicit instruction not to change the call shape RFC-015's shell code would already be calling. RFC-015 has not been implemented — `crates/tekstide/src` contained only `main.rs` before this slice, with no `i18n` module at all. There was no placeholder to replace and no existing call shape to preserve. This slice therefore *establishes* the call shape (`i18n::Catalog`, `Catalog::resolve`, `Catalog::get`) rather than conforming to one RFC-015 already fixed — documented directly on the module so a future reader does not assume RFC-015 defined this and go looking for a divergence that never existed.

**1. Catalog format decision, measured.** Fluent (`fluent-bundle` 0.16.0) added as a direct dependency of `tekstide` alongside `unic-langid` 0.9.6 (for `LanguageIdentifier` parsing in the fallback chain) and `sys-locale` 0.3.2 (OS locale detection).

**Corrected per response 122 Required 1.** The original measurement used `git diff Cargo.lock | grep -c '^+name = '`, which measures the **workspace lock**, not the shipped `tekstide` binary — the workspace also contains `tekstide-gui-spike` (`publish = false`, pulls a large `iced` tree), so that method attributes the spike's resolution to `tekstide` and can hide or misreport real costs. Corrected method, per response 122: `cargo tree -p tekstide --edges normal`, scoped to what the shipped binary actually pulls, measured before/after by temporarily removing the dependency from `crates/tekstide/Cargo.toml`, re-running, and diffing the deduplicated package lists (`cargo tree -p tekstide --edges normal --prefix none | sed 's/ (\*)//' | sort -u`).

**Corrected figures:**
- **Whole `tekstide` binary tree, with Fluent + `sys-locale`: 39 packages total.**
- **Baseline (only `tekstide-core`, no i18n deps): 23 packages.**
- **Net delta: +16** — `displaydoc`, `fluent-bundle`, `fluent-langneg`, `fluent-syntax`, `intl-memoizer`, `intl_pluralrules`, `rustc-hash`, `self_cell`, `syn` (a second version, `v3.0.3`, alongside the `v2.0.118` already pulled by `serde_derive`), `sys-locale`, `thiserror`, `thiserror-impl`, `tinystr`, `type-map`, `unic-langid`, `unic-langid-impl`.
- **`sys-locale` alone measured separately (added with Fluent/`unic-langid` removed): +1**, confirmed against the reviewer's own probe (`cargo tree -p tekstide -i sys-locale` shows `sys-locale` with `tekstide` as its only parent — no shared path through `tekstide-gui-spike`, so the original "+0, already resolved elsewhere" claim was wrong; the true cost is a real, if trivial, +1). Fluent + `unic-langid` alone therefore account for the remaining **+15**.
- The original measurement's claim that `zerofrom`/`zerovec` were part of the cost was also wrong — both are in the *workspace* lock (pulled by something in `tekstide-gui-spike`'s tree) but not in `tekstide`'s own dependency tree at all; they are absent from the corrected package list above.

**Decision: Fluent, not the TOML fallback — unaffected by the correction.** `cargo tree -p tekstide --edges normal` is **39 packages for the entire shipped binary**, Fluent included. Against RFC-014 R3's recorded +345 for the GUI substrate decision, Fluent for native plural categories, gendered forms, interpolation, and asymmetric translation remains plainly proportionate — the decision gets stronger, not weaker, once PR-016-D actually uses the plural-category capability that justifies the cost. Recording the reasoning, not just the outcome, per `implementation-handoff.md`'s explicit instruction, and recording the *method* this time so PR-016-D and RFC-023 do not repeat the lock-diff approach.

**2. Source-locale catalog compiled into the binary.** `crates/tekstide/locales/en.ftl` — a minimal, hand-written FTL file (`app-title`, `project-board-title`) sufficient to prove the machinery; RFC-016 §Non-Goals excludes real translations as content work, and there is no real UI yet (RFC-015 unimplemented) to have real keys for. Compiled in via `include_str!` in `i18n/catalog.rs`, so a missing or corrupt catalog file on disk can never make the application unusable — confirmed by `source_locale_catalog_parses`, and structurally: `catalog::source_locale_bundle()` takes no path argument at all, it embeds the FTL text at compile time.

**3. Lookup, locale selection, and fallback chain.** `crates/tekstide/src/i18n.rs` (+ `i18n/catalog.rs`, `i18n/tests.rs`). `Catalog::resolve(preference, locales_dir)` resolves the active locale once (RFC-016: "runtime locale switching is out of scope for M8") per the precedence RFC-016 §Catalog format and locale model specifies: explicit CLI flag → configuration setting → OS locale (`sys_locale::get_locale`) → source locale. `LocalePreference::configured` is always `None` today — RFC-023 (which supplies it) does not exist yet — the field exists so `resolve`'s signature does not need to change when RFC-023 lands, matching this RFC's own text ("Configuration setting (RFC-023 supplies it through this API)"). `Catalog::get(key)` implements the fallback chain per key lookup: resolved locale → resolved locale's bare language subtag → source locale → the key itself, never blank, never panicking. A miss past the first stage is logged at `eprintln!` under `cfg!(debug_assertions)` only, never as an audit event (a missing translation is not a security decision, per RFC-016's own text).

**Tests (9, all in `i18n::tests`):** `source_locale_catalog_parses`; `an_existing_key_resolves_to_its_value` (baseline); `a_missing_key_renders_as_the_key_itself_never_blank`; `a_missing_locale_falls_back_to_the_source_locale`; `a_region_specific_locale_falls_back_to_its_language_subtag_catalog` (a real `fr.ftl` fixture written to a scratch directory, requested as `fr-CA`); `a_key_missing_from_a_loaded_locale_falls_back_to_the_source_value` (the fallback chain's middle link — a loaded non-source locale missing one specific key, distinct from both "resolves directly" and "missing everywhere"); `cli_flag_takes_precedence_over_configured_locale` (both supplied, confirms the CLI flag is the one actually used); `an_empty_preference_still_resolves_to_a_usable_catalog`; `no_locales_directory_falls_back_to_source_without_panicking` (`locales_dir: None`, e.g. a fresh install with no locales directory yet).

Three ablation-verified, all reverted after confirming failure: the language-subtag fallback branch (disabled → the region-specific-locale test failed, resolving to `en` instead of `fr`); CLI-flag-over-configured precedence (swapped → the precedence test failed, resolving to `es` instead of `de`); key-level fallback to the source locale (disabled → the key-fallback test failed, rendering the literal key `project-board-title` instead of the source value `Project Board`).

**What this slice does NOT do, and why.** No caller exists yet: `main.rs` declares `mod i18n;` and does not call into it, matching PR-016-C's `text_safety` precedent exactly (response 118 Q1: "leave every checklist line unchecked, do not stub a call site — a synthetic call site would make the checklist look satisfied while proving only that the function can be called"). `main.rs`'s existing `shell.render_text()` dump is a pre-RFC-015 debug rendering, not RFC-015's rendered surface, and is out of scope for localization. No CLI flag parsing exists in `main.rs` (`LocalePreference::cli_flag` has no real caller yet either, for the same reason). No second locale is added — RFC-016 assigns that to PR-016-D, "purely to prove the machinery works" once pluralization needs it.

**Required 2, response 122 — `tekstide-core::shell::render_text` collides with PR-016-E, flagged now rather than discovered under enforcement-slice pressure.** `crates/tekstide-core/src/shell.rs::render_text()` is what actually produces the CLI's real output today (confirmed by `cargo run -p tekstide`):

Roughly sixteen hardcoded, user-facing English strings (`"content status: "`, `"(project root)"`, `"active file: none"`, and the rest) — in **`tekstide-core`**, which by design cannot reach `crates/tekstide/src/i18n.rs` (localization is a shell-crate presentation concern; `tekstide-core` owns state and policy, never rendering). Separately, `en.ftl` currently holds two keys (`app-title`, `project-board-title`) against roughly sixteen live strings in `render_text` alone — correct for a machinery-proving slice with no real UI yet, noted here so PR-016-E's eventual catalog-completeness check is not surprised by the gap.

### PR-016-C — Text safety: escape and isolate

**Module:** `crates/tekstide-core/src/text_safety.rs` (+ `text_safety/tests.rs`), newly registered in `lib.rs`. Public API: `is_format_char`, `is_untrusted_display_control`, `escape_untrusted_chars(text: &str) -> String`, `DisplayText` (opaque wrapper, no public constructor other than below), `quote_untrusted(text: &str) -> DisplayText`.

**Consolidation, not new invention.** The character-escaping policy (Unicode `Cc`+`Cf` categories → visible `<U+XXXX>` markers) already existed, implemented ad hoc inside `approval::coordinator` under RFC-021 PR-021-E1/response-115 review pressure, before this RFC existed to own it. RFC-016's own README (2026-07-30 addendum) forced the answer to Open Question 1: the function lives in `tekstide-core`, shared, not shell-local. This slice: (1) moved `is_format_char`/`is_escaped_control` (renamed `is_untrusted_display_control`) and the `<U+XXXX>` substitution loop out of `approval/coordinator.rs` verbatim into `text_safety.rs`; (2) rewired `approval::coordinator::display_entry`/`needs_quoting` to call `crate::text_safety::escape_untrusted_chars`/`is_untrusted_display_control` instead of a private copy; (3) added the whole-string API (`quote_untrusted`/`DisplayText`) that `implementation-handoff.md` specifies, for future single-value untrusted-text surfaces (Project Board rows, notifications, viewers) that have no argv-shaped per-entry quoting need.

**Split between the shared module and `approval::coordinator` is deliberate, per the README's explicit carve-out:** the character-escaping half (`Cc`/`Cf` → `<U+XXXX>`) is text-shaped and must not be duplicated, so it moved. The per-entry POSIX-style quoting (`SHELL_METACHARACTERS`, `needs_quoting`'s whitespace/metacharacter checks, single-quote wrapping) is argv-shaped — "argv is a vector of entries," not "text contains untrusted characters" — and has no equivalent in `text_safety`'s single-string API, so it stayed in `approval::coordinator`.

**Zero behavior change confirmed.** Every pre-existing `approval::tests::coordinator::display_command_*` test (6 tests, including the response-115 ten-codepoint probe) passes unchanged after the refactor — same inputs, same outputs, only the implementation moved. Ablation-verified the wiring is real, not a leftover stale copy: temporarily broke `text_safety::is_untrusted_display_control` (`|_| false`) and confirmed both the new `text_safety` tests **and** all pre-existing `approval::tests::coordinator::display_command_*` bidi/control tests failed identically (5 failures across both modules), then restored — proving `approval::coordinator` now genuinely depends on the shared implementation rather than retaining a divergent local one.

**Isolation (`quote_untrusted`).** Wraps the escaped text in Unicode bidi isolate marks: First Strong Isolate (U+2068) ... Pop Directional Isolate (U+2069). Since escaping already converts every live directionality/format control (including U+2068/U+2069 themselves, if present in the untrusted input) into an inert visible marker before the wrap is added, the isolate wrapping is a second, structural layer of defense — RFC-016 §Security point 2 read literally ("the span is directionally isolated ... regardless of what it contains"), not a substitute for point 1.

**Type-safety choice, per `implementation-handoff.md`'s "prefer that" guidance:** `DisplayText` has no public constructor other than `quote_untrusted` — a future widget API that requires `DisplayText` rather than `&str` cannot be handed raw untrusted text at all, mirroring the same "parse, don't validate" reasoning RFC-015 applies to its input classes and RFC-021 applies to `VerifiedCwd`.

**Tests (`text_safety/tests.rs`, 7 new):**
- `every_bidi_and_format_probe_escapes_to_its_visible_marker` — carries over the exact ten-codepoint set from `approval::tests::coordinator` (U+202E, U+2066, U+200E, U+200F, U+061C, U+200B, U+200C, U+200D, U+00AD, U+FEFF), per the README's explicit instruction, so the canonical implementation is tested at least as hard as the copy it replaces.
- `the_full_isolate_initiator_and_terminator_range_is_escaped` — the exact `U+2066..U+2069` range the checklist names, including U+2069 (PDI) specifically: an attacker-supplied PDI inside untrusted text is escaped to a literal marker and cannot be mistaken for, or prematurely close, the isolate `quote_untrusted` itself adds.
- `the_trojan_source_pattern_is_defeated` — a string built exactly like the classic Trojan Source exploit (`good` + RLO + `exe.`); confirms the RLO survives only as an inert `<U+202E>` marker and the stripped-of-wrapper character sequence matches the logical input order exactly, character for character.
- `an_unterminated_override_cannot_affect_adjacent_trusted_text` — an untrusted span with an RLO and no matching PDF, composed inline between two trusted labels; confirms no live bidi/format control survives anywhere in the composed string except the two isolate marks this module itself added, and that the trusted labels are untouched. **Honestly scoped:** this checks structural properties (marker substitution, isolate-mark presence), not a full Unicode Bidi Algorithm resolution — this crate does not implement one, and does not need to, since escaping removes every live directional instruction before isolation is even relevant.
- `legitimate_rtl_letters_are_not_escaped` — genuine Arabic letters (not bidi *control* characters) pass through byte-for-byte unescaped, directly proving the over-escaping risk RFC-016 §Risks flags is not realized.
- `escaping_does_not_mutate_the_caller_s_original_value` — both functions take `&str`, never `&mut str`; explicit regression guard against a future signature change reintroducing ingest-time mutation.
- `an_empty_string_does_not_panic_and_produces_the_bare_isolate_wrapper` — an empty untrusted field is a legitimate input, not a special case requiring different handling.

**Byte fidelity, honestly scoped.** Verified structurally (both functions are pure `&str -> String`/`DisplayText`, no caller value is ever mutated) and verified against the one real integration point that exists today: `approval::coordinator`'s pre-existing `sentinel_command_text_never_reaches_the_durable_audit_store` (unchanged by this refactor) proves neither raw command text nor the escaped display string reaches the durable audit store. **Not yet verified against an RFC-011 transcript path**, because no transcript code calls into `text_safety` at all — there is no integration point to test yet. This is recorded as an honest gap, not silently assumed.

**What this slice does NOT do, and why — RFC-015 has not been implemented.** `crates/tekstide/src` contains only `main.rs`; there is no application shell, no dialog surface, no Project Board row rendering, no notification surface, no audit or transcript viewer, and no editor surface anywhere in the tree. RFC-016 §Security's "where this applies" table (approval/trust/paste/destructive/safe-close dialogs, Project Board rows, notifications, viewers) and the editor/terminal exceptions therefore have **nothing to apply `quote_untrusted` to yet** — every one of those checklist lines is left unchecked below, not on a technicality but because the surfaces genuinely do not exist. `approval::coordinator`'s argv rendering is the one real, live call site, and it already used (now shares) this exact policy before this slice began. This mirrors RFC-021's "headless" precedent: the primitive is built, tested, and reviewable in isolation; wiring it into real surfaces is necessarily deferred to whichever slice first builds each surface (RFC-015's shell, RFC-022's approval dialog, and so on).

**Required 1 — the escape set's boundary was `Cc` + `Cf`, and the reviewer's probe found the same response-115-class defect one Unicode general category over.** `impor<ZWSP>tant.txt` (response 115's finding, `Cf`) and `impor<HANGUL FILLER>tant.txt` (this finding, `Lo` — a *letter*) are the same display-spoofing shape: two different logical strings that render identically because a genuinely invisible codepoint sits outside whichever category rule was checked. Probed and confirmed: U+3164 (HANGUL FILLER), U+FFA0 (HALFWIDTH HANGUL FILLER), U+115F (HANGUL CHOSEONG FILLER), U+1160 (HANGUL JUNGSEONG FILLER) — all `Lo` — and U+2065 (`Cn`, unassigned, named explicitly by RFC-016 §Security point 3) all passed through unescaped under the `Cc`+`Cf` rule. **Fix:** the predicate now covers Unicode's **`Default_Ignorable_Code_Point`** property — the standard concept for exactly this — via a new private `is_default_ignorable_extra` function covering the property's members not already in the `Cf` table (Hangul fillers, variation selectors, Mongolian free variation selectors, U+2065, and the associated unassigned/reserved ranges), hand-transcribed against Unicode 15.0 with the same not-mechanically-verified caveat as the existing `Cf` table. **U+2800 BRAILLE PATTERN BLANK decided explicitly, not escaped:** it renders blank to a sighted non-Braille-reader (the same visual symptom) but is category `So`, not `Default_Ignorable_Code_Point`, and Braille content is legitimate text a Braille-literate user is entitled to see — recorded as a fixture (`braille_pattern_blank_is_not_escaped`) so a future change is a visible diff. **Required 2 — the doc claimed a category rule; the code was an unversioned snapshot.** `is_format_char`'s doc previously claimed to cover "whatever invisible-character shape nobody has thought of yet" — a promise a hand-transcribed table can never make good on, which Required 1's finding directly disproved. Corrected: the doc now states the table is a hand-transcribed snapshot of Unicode 15.0's `Cf` category, not mechanically verified, and records a known open discrepancy at the upper bound of the Shorthand Format Controls block (`0x13438` here vs. response 115's `0x1343F`) without resolving it — the point being that the discrepancy is now checkable rather than silently trusted. `is_default_ignorable_extra` carries the same version-and-caveat documentation.

**Required 3 — `is_format_char` narrowed to private.** It was `pub`, which invited a caller to assemble a divergent escape rule from its parts — exactly the duplication this module exists to end. `is_untrusted_display_control`, `escape_untrusted_chars`, `quote_untrusted`, and `DisplayText` remain the public API; `is_format_char` and the new `is_default_ignorable_extra` are both private implementation detail.

This is not merely theoretical: the U+2065 finding above is a real, demonstrated case of an unassigned codepoint needing coverage, and RFC-016 §Security explicitly names "unassigned-but-rendering-invisible codepoints" as in scope. U+2065 itself is hand-covered now (the one case that could not wait); the rest of `Cn` is deferred to PR-016-B's already-required Fluent dependency measurement, folding in a small Unicode-properties crate for the same decision, with numbers, rather than adding table entries under slice pressure.

### PR-016-D — Pluralization and interpolation

**Why now, not deferred further — response 123/124's own reasoning, not asserted independently.** `Catalog::get(&self, key: &str) -> String` (PR-016-B) takes no arguments, so nothing using it can express an interpolated value — including every count RFC-015 PR-015-D needs to render with `CountDisplay` fidelity. Without this slice, PR-015-D would either hardcode counts or invent a second, ad hoc interpolation path outside the catalog. **PR-016-D unblocks PR-015-D**, which is why it lands before RFC-015 rather than after, even though this cycle has otherwise been headless work.

**1. `Catalog::get_with_args(&self, key: &str, args: &CatalogArgs) -> String`** (`i18n.rs`), alongside the existing `get`. Both share one internal implementation (`get_with_args_impl`) taking `Option<&FluentArgs>`, so the fallback chain (resolved locale → source locale → the key itself) is identical for both — interpolation does not have a second fallback implementation to drift from the first. **The public signature changed after response 125's Required 1** (see the "Response 125 follow-ups" note below) — `CatalogArgs` is this module's own builder type, not a re-export of `fluent_bundle::FluentArgs`.

**2. The design constraint from response 123/124, met without inventing a bespoke argument type.** `tekstide_core::project_board::CountDisplay` has four variants -- `KnownCount(u32)` plus three non-numeric states -- and "an interpolation API that only accepts numbers... [makes] three of the four states... inexpressible." `FluentValue` already *is* "either a number or a symbolic state" (its `Number`/`String` variants), and Fluent's own select-expression syntax already matches literal string variants alongside CLDR plural categories against the *same* selector variable. So `$count` in `blocked-automation-count` (`en.ftl`/`pl.ftl`) carries a `FluentValue::Number` for a known count (plural-category selection applies) or a `FluentValue::String` naming one of the three non-numeric states (matched as a literal variant) -- one key, one lookup call, no second API. Proven by `interpolation_expresses_every_count_display_state_through_one_key`, including the explicit assertion that no non-numeric state ever renders as `0` -- RFC-015 §"`CountDisplay` fidelity... never as zero"'s requirement, tested at the catalog layer now rather than left to be discovered wrong later. **Not solved: which concrete Rust type bridges `CountDisplay` to `FluentValue`.** That conversion is RFC-015 PR-015-D's to write, per response 123/124's explicit "do not solve that in PR-016-D" -- this slice proves the catalog *can* express all four shapes, not that any calling code yet does.

**3. A genuine discovery, not anticipated in advance: Fluent wraps every interpolated placeable in Unicode bidi isolate marks (First Strong Isolate / Pop Directional Isolate) by default.** `FluentBundle`'s `use_isolating` option defaults to `true` and was never touched by this slice. `{$count}` in the FTL source therefore renders as `\u{2068}9\u{2069}`, not bare `9` -- discovered the hard way, as a failing string-equality assertion, before being turned into a documented, asserted property (`plural_categories_apply_for_english_too_with_its_simpler_one_other_split`). This is exactly RFC-016 §Security point 2's isolation defense, applied by the underlying library to *every* interpolated value automatically, trusted or not -- a real, free layer of the policy this RFC already required, not something this slice built.

**4. The security boundary response 123/124 implicitly raised (interpolation vs. `text_safety`) is tested directly, in both directions.**
   - **No injection.** `interpolated_values_cannot_inject_fluent_syntax`: a `&'static str` literal containing literal FTL-reference-shaped text (`"{ -brand-name } { $secret -> *[other] leaked }"`), passed via `CatalogArgs::trusted_symbol`, renders byte-for-byte as given (modulo the isolate wrapping from point 3) -- Fluent treats argument values as opaque literals, never re-parsed as FTL source, so an interpolated value cannot alter the structure of the message it was interpolated into.
   - **No auto-escaping, and the API no longer lets a caller find out the hard way.** The original PR-016-D submission had a test (`interpolation_does_not_substitute_for_text_safety_escaping`) proving a raw `U+202E` survived interpolation unescaped -- response 125 Required 1 found that this was not a documented caveat but a live bypass, since the public API had no type-level barrier stopping a caller from interpolating raw untrusted text in the first place. See "Response 125 follow-ups" below for the fix and its replacement test.

**5. Second locale: Polish (`pl`), loaded from the real, shipped `crates/tekstide/locales/pl.ftl`**, not a throwaway test fixture -- `real_polish_catalog_loads_from_the_shipped_locales_directory` and `plural_categories_differ_correctly_for_polish` both resolve through `Catalog::resolve` against the actual `locales/` directory (`env!("CARGO_MANIFEST_DIR")`-relative), so the tests prove the file this crate ships works, not a copy of it. Polish was chosen over an RTL locale (RFC-016 §Open Questions' other option) because its CLDR plural categories (`one`/`few`/`many`/`other`) differ from English's (`one`/`other`) in exactly the way that stresses the machinery response 123/124 needed proven; RTL rendering is already covered at the `text_safety` layer (PR-016-C's `legitimate_rtl_letters_are_not_escaped`) via genuine Arabic text, so a second RTL proof point here would have been redundant rather than additive. Three counts (1, 3, 5) chosen to land in three distinct real Polish CLDR categories (`one`/`few`/`many`), asserted to produce three genuinely different rendered strings -- not merely that a second `.ftl` file parses.

**Ablation-verified.** Temporarily made `pl.ftl`'s `few` and `many` variants render identical text and confirmed `plural_categories_differ_correctly_for_polish` failed (`few.contains("zablokowane automatyzacje")` false) -- proving the three-way distinction is real `intl_pluralrules`-driven CLDR selection, not three branches that happen to produce the same string by coincidence. Restored immediately after observing the failure.

**Translation quality disclaimer.** The Polish word forms in `pl.ftl` are plausible but not professionally reviewed -- RFC-016 §Non-Goals excludes real translation as content work, and this file's only job is to exercise genuinely different plural categories, which it does regardless of whether the grammar is publication-quality.

**Response 125 follow-ups (both Required, applied 2026-07-31 on top of the `a311cba` submission above).**

**Required 1 — untrusted interpolation bypassed `text_safety` entirely.** The original `get_with_args` re-exported `fluent_bundle::{FluentArgs, FluentValue}` publicly, so `FluentValue::from(any_runtime_str)` compiled regardless of whether the string was trusted -- probed by the reviewer with a project-name-shaped `U+202E` override that survived interpolation live, contained by Fluent's isolate wrapping but not escaped, indistinguishable from any other localized text. Fixed by making the unsafe path unconstructible, the same shape of fix as `DisplayText` (PR-016-C), `VerifiedCwd`, and `RunCapabilityToken` (RFC-021): `fluent_bundle::{FluentArgs, FluentValue}` are no longer re-exported at all; `i18n::CatalogArgs` is the only way to build interpolation arguments, with exactly three constructors --
- `number(name, n)` -- bounded by a sealed `CatalogNumber` trait to genuine numeric primitives only, so a caller cannot smuggle a string through a generic numeric-conversion bound.
- `untrusted(name, &DisplayText)` -- takes `tekstide_core::text_safety::DisplayText`, obtainable only via `quote_untrusted`; there is no constructor on `CatalogArgs` that accepts a raw `&str` for untrusted text, so a caller cannot skip `text_safety` and still compile.
- `trusted_symbol(name, &'static str)` -- for `CountDisplay`-shaped state names and other compile-time literals; the `'static` bound excludes runtime/attacker-influenceable data by construction.

  **Verified the raw path no longer typechecks.** `tekstide` is a `[[bin]]`-only crate with no `[lib]` target, so a `compile_fail` doctest is not available (doctests link against a library crate's public API, which does not exist here) -- response 125 offered `qa-evidence.md` note as the alternative, taken here. Confirmed directly instead: temporarily appended `CatalogArgs::new().untrusted("name", "raw str")` (a bare `&str`, not `&DisplayText`) to `i18n/tests.rs` and ran `cargo build -p tekstide --all-targets`; it failed with `E0308: expected &DisplayText, found &str`, then the probe line was removed. `.number("count", "not_implemented")` similarly does not typecheck (the sealed `CatalogNumber` trait is not implemented for `&str`), though this was not separately re-verified since the mechanism (a private, unimplementable-outside-the-module trait bound) is the same one already exercised in RFC-021.

  **New test proving the fix closes the exact gap the reviewer's probe demonstrated**, `an_escaped_untrusted_value_survives_correctly_through_interpolation`: builds a `DisplayText` via `text_safety::quote_untrusted` on `"proj\u{202E}gpj.exe"` (the reviewer's own probe text), interpolates it via `CatalogArgs::untrusted`, and asserts the rendered result contains no live `U+202E` and does contain the escaped `<U+202E>` marker. Replaces `interpolation_does_not_substitute_for_text_safety_escaping`, whose premise (raw untrusted text reaching interpolation) is no longer reachable via the public API. **Ablation-verified**: temporarily changed `CatalogArgs::untrusted` to un-escape the marker back to a live `U+202E` before setting the Fluent value (simulating the pre-fix bug) -- the new test failed with the live override present in the rendered output (`"...\u{202e}gpj.exe..."`); restored immediately after observing the failure.

### PR-016-E — Enforcement

**Unblocked 2026-08-01** by RFC-015 PR-015-D's decision to keep `tekstide_core::shell::render_text` (response 130). Four mechanical checks, all in `crates/tekstide/src/i18n/enforcement.rs`:

1. **`no_raw_string_literal_is_passed_to_text_anywhere_in_the_crate`** — the canonical home for "no user-facing string is hardcoded" in `crates/tekstide`. Absorbs PR-015-B's identical scan (response 128), which lived in `shell::tests` only because `shell.rs` was this crate's one module when it was written; that copy is deleted, `shell/tests.rs` now points to this one in a comment. One mechanical check for one policy, not two that can drift apart.
2. **`tekstide_core_hardcoded_strings_match_the_closed_exemption_list`** — see below.
3. **`i18n_never_re_exports_a_raw_fluent_type`** — response 126's recommended guard, made mechanical (see PR-016-D's write-up above). Scans `i18n.rs` and `i18n/catalog.rs` for a `pub use fluent_bundle`/`FluentArgs`/`FluentValue` re-export at any line. `tekstide` is `[[bin]]`-only, so no `compile_fail` doctest was available; this is what response 126 asked for instead.
4. **`every_source_locale_key_resolves_in_every_shipped_locale`** and **`report_catalog_keys_unused_by_any_render_call`** — catalog completeness and its advisory mirror. The unused-key report is advisory (`task-breakdown-pr-plan.md`'s own word) and deliberately never fails; currently empty (every key is referenced somewhere in `crates/tekstide/src`).

**Why `tekstide-core` is scanned by a fixed file list, not the whole crate.** Tried first, by inspection: a blanket "any string literal is a violation" scan over all of `tekstide-core` would need to exempt 43 non-test files containing a space-containing literal — SQL migration statements, ANSI/VT escape sequences, error `Display` text, audit codes. An exemption list that long is not closed in any reviewable sense; it is the noise-nobody-acts-on failure mode enforcement exists to avoid. So the scan names three files (`shell.rs`, `project_board.rs`, `project/metadata.rs`) explicitly. **Disclosed limitation, not silently accepted**: a brand-new `tekstide-core` module that starts producing user-facing text somewhere else would not be caught until added to the target list.

## Known Limitations

- **Confusable and homoglyph attacks are not addressed.** Full detection is heavy and error-prone; a partial implementation would imply a guarantee that does not exist. A later RFC may revisit if command approval proves to need it.
- **RTL layout mirroring is deferred.** Text renders correctly RTL; surrounding layout stays LTR.
- **Terminal-grid bidi reordering is out of scope by design** — real terminals do not implement it, and reordering would break cursor and column arithmetic.
- **Terminal wide-cell CJK is a genuine gap owned by RFC-017**, not by this RFC.
- Runtime locale switching is out of scope for M8; selection resolves once at startup.
- **`text_safety::quote_untrusted` has no real caller yet beyond `approval::coordinator`'s (pre-existing, argv-shaped) usage of the character-escaping half.** RFC-015's shell has not been implemented (`crates/tekstide/src` contains only `main.rs`), so there is no dialog, Project Board row, notification, audit viewer, transcript viewer, or editor surface in the tree to apply the whole-string API to. The primitive is built and tested in isolation, matching RFC-021's "headless" precedent; every "applied to: <surface>" line in the acceptance checklist is unchecked for this reason, not because the primitive is unproven.
- **Byte fidelity is verified against the audit path (`approval::coordinator`'s existing sentinel test) but not against an RFC-011 transcript path** — no transcript code calls into `text_safety` yet, so there is no integration point to test.
- **The terminal-surface "no escaping, no reordering" exception is not something this slice implemented** — it is the terminal's pre-existing behavior (no bidi handling exists there at all, confirmed by RFC-014 C10 and `tekstide-gui-spike`'s filter tests), not a deliberate opt-out of a shared render path the terminal would otherwise go through. Recorded as correct-by-absence rather than claimed as an implemented, documented exception under this RFC.
- **`i18n::Catalog` has no real caller yet.** RFC-015's shell has not been implemented, so there is no lookup call site to wire it into — the same "headless" shape as `text_safety` above, and for the same underlying reason (RFC-015). `main.rs` declares the module (`#[allow(dead_code)]`) but does not call it; no synthetic call site was added, matching response 118 Q1's explicit ruling against stubbing.
- **`LocalePreference::configured` (RFC-023's configuration setting) is always `None`.** RFC-023 does not exist yet. The field and its place in the precedence order exist so `Catalog::resolve`'s signature does not need to change when RFC-023 lands; until then, only the CLI-flag and OS-locale paths are reachable in practice.
- **No CLI flag parsing exists in `main.rs`.** `LocalePreference::cli_flag` is exercised by this slice's own tests, not by any real command-line argument handling — `main.rs`'s argument loop is unrelated (it takes project paths, not locale flags).
- **Resolved in PR-016-D: a second locale (Polish, `pl`) now has a real catalog file** (`crates/tekstide/locales/pl.ftl`), loaded from the real shipped `locales/` directory in its own tests, proving genuinely different CLDR plural categories rather than only that a second `.ftl` file parses. Translation quality is not reviewed (RFC-016 §Non-Goals: real translation is content work) -- only the plural-category machinery is proven.
- **`Catalog::get_with_args`'s caller-facing conversion from `CountDisplay` to `FluentValue` does not exist yet.** PR-016-D proves the catalog *can* express all four `CountDisplay` states through one key; RFC-015 PR-015-D owns writing the actual conversion code and calling it, per response 123/124's explicit "do not solve that in PR-016-D."
- **`CountDisplay::label()` (`tekstide-core::project_board`) is a fourth hardcoded-string site the catalog cannot reach**, alongside `render_text`'s ~16 strings -- see the PR-016-B write-up's Required 2 entry and the PR-016-D note added beside it for the full detail. **Decided in RFC-015 PR-015-D (response 130):** the real GUI surface (`crates/tekstide/src/surface/board.rs`) never calls `label()` at all -- every `CountDisplay`/`AttentionState` field routes through `CatalogArgs::number`/`trusted_symbol` into real `en.ftl` keys instead, mechanically enforced by `shell::tests::no_count_display_or_attention_label_is_called_anywhere_in_the_crate`. **Not fully closed**: `label()` keeps its one remaining caller, `tekstide_core::shell::render_project_board` (part of `render_text`, which PR-015-D also decided to keep -- see below). So `label()` is unreachable from the real rendered surface, but still technically "outside the catalog's reach" from the harness's perspective. PR-016-E's scan-scope note should read this as: the *shipped GUI* no longer has this gap; the *pre-GUI test harness* still does, by design.
- **`tekstide_core::shell::render_text` is kept, not deleted, by explicit PR-015-D decision (response 130).** The RFC-015 handoff README invited its deletion ("PR-015-D is expected to delete it... If you do not delete it, say so explicitly"). Investigated rather than assumed: `render_text` is the primary assertion mechanism for roughly twenty `tekstide-core::shell::tests` (route transitions, mode switching, terminal panes, document editing, explorer scanning) that PR-015-D's own scope does not touch. Deleting it would mean rewriting all twenty to structured assertions -- a substantial `tekstide-core` test-suite refactor, not a side effect of Project Board rendering, and itself a `tekstide-core` change that should be raised and planned on its own rather than folded into an unrelated GUI slice. **PR-016-E's scan scope must still exclude `tekstide-core::shell::render_text` and `CountDisplay::label()`'s one remaining caller inside it** -- this was RFC-016 PR-016-B's original scan-scope obligation, and it remains live, not resolved by PR-015-D landing.
- ~~Fluent's automatic bidi isolate-mark wrapping of interpolated placeables (`use_isolating`, default `true`) has not been evaluated against every possible downstream renderer.~~ **Closed by RFC-015 PR-015-B (response 128).** `iced`/`cosmic-text` is now a real rendering surface: `status_bar_summary` produces `⁨Project Board⁩ | ⁨⁨0⁩ projects⁩` (isolate marks and all, asserted literally in `shell::tests`), and the screenshot (`rfcs/handoffs/015-application-shell-and-rendered-surface-model/evidence/pr-015-b/shell-chrome-over-real-state.png`) shows it rendering clean as `Project Board | 0 projects` -- no stray glyphs, no tofu. `iced` consumes U+2068/U+2069 as directional instructions rather than drawing them. Added here so PR-016-E inherits a complete list rather than two of three sites.
- **A fourth site (response 132, found while reviewing RFC-015 PR-015-D): `tekstide-core::project_board::ProjectBoardRow`'s `trust_label`, `security_mode_label`, `availability_label`, and `blocked_automation_labels`.** These are now genuinely rendered by a real GUI surface (`crates/tekstide/src/surface/board.rs`), not merely present in unused core data — real, user-facing, hardcoded-English strings in a shipped rendered surface. Not a security gap (they are trusted, fixed-set content, not filesystem-derived), but exactly what PR-016-E's scan exists to find. - **PR-015-B's own crate-tree seam scan (`crates/tekstide/src/shell/tests.rs`) and PR-016-E's future no-hardcoded-strings scan will overlap in policy (response 128).** PR-015-B's scan covers `crates/tekstide`'s own source for raw string/colour/font-size literals reaching `iced` widgets; PR-016-E's scan is expected to cover `tekstide-core` (and possibly `tekstide` too) for the same underlying policy ("no hardcoded user-facing string"). Two mechanical checks enforcing one policy is how they drift apart, the same consolidation lesson `text_safety` produced (RFC-016 PR-016-C: one shared escape function rather than two divergent ones). When PR-016-E lands, one scan should absorb the other rather than both surviving independently — flagged here while the duplication is one line, not two harnesses.
- **Full Unicode `Cn` (unassigned-codepoint) coverage is deliberately deferred to PR-016-B's dependency measurement, not hand-rolled** (response 118).
