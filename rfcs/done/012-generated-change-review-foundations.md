## Summary

RFC-012 defines the first headless model and harness for detecting, summarizing, and reviewing file changes associated with Tekstide-created AgentRuns. It completes the non-GUI "review foundations" part of M6 after RFC-011 added bounded transcript retention.

The design grows the existing `ChangeSet` model into a content-safe review object linked to an AgentRun when possible. The first implementation should detect changed file paths and review state transitions without claiming rendered diff UI, hunk-level accept/reject, durable audit persistence, command approval, or automatic rollback.

Durable audit is now expected to become RFC-013.

## Motivation

AgentRun transcript retention explains what happened in terminal output, but it does not by itself identify which project files changed. Tekstide needs a small, reviewable model that says:

- which files changed during or after an AgentRun;
- which AgentRun likely owns the change set;
- whether the change set still needs user review;
- what bounded metadata can be shown without leaking file contents;
- which future audit and GUI surfaces can reference later.

Without this layer, Project Board review counts remain generic, AgentRun completion cannot become review-ready truthfully, and durable audit would have no stable generated-change vocabulary.

## Goals

- Define generated-change review vocabulary for headless/model implementation.
- Link detected change sets to AgentRuns when the association is credible.
- Snapshot baseline project state before an AgentRun or review scan.
- Detect changed project-relative file paths after an AgentRun or explicit scan.
- Keep summaries metadata-only by default: ids, paths, counts, byte/size categories, state, timestamps, and bounded error categories.
- Track review state transitions: unreviewed, accepted, partially accepted, rejected, superseded.
- Feed existing project runtime summaries and close-resource review counts.
- Treat changed files as untrusted project content.
- Provide implementation slices and QA evidence requirements for M6 closeout.

## Non-Goals

- Rendered diff/review UI.
- Hunk-level accept/reject UI or patch application.
- Automatic rollback, stash, branch management, or destructive cleanup.
- Durable audit persistence, audit migrations, or audit database schema.
- General command approval or managed adapter command interception.
- Search indexing over file contents or transcripts.
- Secret detection or redaction of generated file contents.
- Full file watcher behavior or multi-document conflict workflows.
- Cross-platform filesystem watcher evidence.
- Claiming that all changes were generated by the AgentRun when the association is only heuristic.

## Design Principles

1. **Reviewable before durable.** Define stable review events and states before RFC-013 durable audit stores them.
2. **Metadata first.** Summaries must not include file contents, transcript snippets, prompts, environment values, or shell history.
3. **Association is explicit.** A ChangeSet may be AgentRun-linked, unlinked, or ambiguous. Tekstide must not overclaim authorship.
4. **Project root remains the boundary.** Detection scans project-relative paths under the ProjectSession root only.
5. **Git is a source, not a requirement.** Git status is the preferred first detector when available; a filesystem snapshot fallback may exist for non-Git projects.
6. **No hidden destructive action.** Review state changes are metadata decisions. They must not edit files, delete files, run commands, or revert changes.

## Review Model

RFC-012 extends the existing `ChangeSet` direction with a review-focused model.

Core concepts:

```text
ReviewBaseline
├─ project_id
├─ agent_run_id optional
├─ captured_at
├─ detector
└─ baseline_ref

GeneratedChangeSet
├─ id
├─ project_id
├─ agent_run_id optional
├─ baseline_snapshot_ref optional
├─ changed_files
├─ artifact_refs
├─ summary
├─ detection_state
├─ association_confidence
├─ review_state
├─ created_at
└─ updated_at
```

The exact Rust names may differ. The implementation may continue using `ChangeSet` if it grows the needed fields and helpers.

## Detection Sources

Initial detection should support these sources:

| Source | Behavior |
| --- | --- |
| Git status | Prefer `git status --porcelain`-equivalent metadata or a safe library equivalent where available. |
| Filesystem snapshot | Compare project-relative file metadata captured before and after a run for non-Git projects or tests. |
| Explicit caller-provided paths | Accept reviewed, project-relative paths from a future adapter or harness without trusting them blindly. |

Detection must classify source availability:

- complete;
- unavailable;
- unsupported repository state;
- partial because limits were hit;
- failed with bounded diagnostics.

The detector must not read or store file contents unless a later reviewed diff preview policy allows it. Path-only and metadata-only detection is sufficient for RFC-012.

## Git Detector Safety

If PR-012-C uses Git through a subprocess, the implementation must treat that subprocess as a security boundary:

- use a reviewed non-project-local Git executable;
- invoke Git directly without a shell;
- use a deterministic argument vector, not Git aliases;
- avoid project-local `PATH` preference;
- pass only a sanitized environment;
- avoid workspace hooks and config-driven automation;
- bound execution time and captured output;
- return bounded diagnostics without file contents, diff hunks, prompts, transcript snippets, environment values, or shell history.

If these guarantees cannot be made, Git detection must report `unavailable` or `unsupported` and fall back to metadata-only filesystem detection where available.

A safe library implementation can satisfy Git detection without subprocess launch claims, but implementation review must still verify that it reads metadata only and does not execute workspace automation.

## Path and Privacy Rules

Changed files must be represented as project-relative paths after root containment validation.

Rules:

- absolute input paths must canonicalize under the ProjectSession root before conversion to project-relative paths;
- relative paths must be normalized and must not escape the project root through `..`;
- symlinks and platform-specific link behavior must not allow a path outside the project root to be reported as an ordinary in-project file without an explicit status;
- summaries and errors must not include file contents;
- paths may be shown as metadata, but very large path lists should be bounded by count and truncation metadata;
- transcript bytes must not be scanned to infer changed file contents.

## AgentRun Association

Association should be conservative.

Strong association:

- baseline is captured immediately before a Tekstide-created AgentRun starts;
- scan runs after that AgentRun reaches completed, failed, cancelled, or review-ready state;
- the ProjectSession has no overlapping unreviewed AgentRun baseline that could own the same changes.

Weak or ambiguous association:

- multiple AgentRuns overlap;
- baseline is missing;
- detector ran long after process completion;
- AgentRun is detached or orphaned and Tekstide lacks independent reviewed evidence that the process boundary is closed;
- project already had unreviewed changes before launch;
- changed paths are caller-provided without a trusted adapter.

When association is ambiguous, the model should create an unlinked or weakly linked ChangeSet rather than assigning authorship as fact.

## Review State Semantics

Review state is metadata only:

| State | Meaning |
| --- | --- |
| Unreviewed | ChangeSet requires user attention. |
| Accepted | User or harness marked the whole ChangeSet reviewed/accepted. |
| PartiallyAccepted | Some files or later hunk decisions were accepted, but not the whole ChangeSet. |
| Rejected | User or harness rejected the ChangeSet as a review decision. No file edits are implied. |
| Superseded | A later ChangeSet or rescan replaced this review target. |

Transitions should be explicit and validated. A rejected state must not imply rollback. An accepted state must not imply tests passed.

## Runtime and Close Integration

ProjectSession should continue deriving review counts from unreviewed ChangeSets. RFC-012 should make that count more meaningful by ensuring AgentRun-linked detected changes enter the collection with truthful review state.

When an AgentRun completes with detected changes, the AgentRun may transition to `ReviewReady` instead of `Completed` if existing lifecycle rules allow it. Terminal/runtime lifecycle remains process truth; ChangeSet review state is generated-work review truth.

Safe-close summaries may count unreviewed ChangeSets but must not list file contents or diffs.

## Privacy and Security Rules

- Changed file summaries may include ids, project id, AgentRun id, project-relative paths, counts, review state, detector source, timestamps, and bounded error categories.
- Summaries must not include raw file contents, diff hunks, transcript snippets, prompt text, environment values, or shell history.
- Generated files remain untrusted project content.
- A malicious AgentRun may modify files and metadata in surprising ways; review status is not a safety proof.
- The design does not claim secret detection or redaction.
- The design does not claim durable audit. RFC-013 must decide which review events are persisted.

## Data Model Impact

Expected model additions or refinements:

- review baseline metadata;
- generated change detector result;
- detection source/status;
- association confidence or equivalent authorship caveat;
- bounded path-list summary;
- review state transition helper;
- AgentRun to ChangeSet attachment helper;
- ProjectSession generated-change scan or attach operation.

Existing `ChangeSet` may remain the root entity if it can represent the required metadata without content leakage.

## Test and Evidence Requirements

- Model tests for review state transitions.
- Ownership tests for cross-project ChangeSet rejection.
- Path tests proving changed paths cannot escape the ProjectSession root.
- Privacy tests proving summaries/errors contain no file contents or transcript snippets.
- Detector tests for created, modified, deleted, and renamed path metadata where practical.
- Detector-unavailable tests for non-Git or unsupported repository state.
- Association tests for linked, unlinked, and ambiguous AgentRun scenarios.
- ProjectSession tests proving unreviewed ChangeSets update review counts and close-resource summaries.
- Regression tests proving accepted/rejected review state does not edit files or imply tests passed.

## Acceptance Criteria

- Generated-change review has a stable headless model.
- ChangeSets can be linked to AgentRuns when association is credible.
- Ambiguous associations remain explicit and do not overclaim authorship.
- Project-relative path detection is root-contained.
- Summaries and diagnostics remain content-free.
- Review state transitions are explicit and tested.
- ProjectSession review counts reflect unreviewed detected ChangeSets.
- Durable audit, rendered GUI review surfaces, hunk-level patch application, rollback, search indexing, secure deletion, and redaction remain non-claims.

## Risks

- **Authorship overclaim.** Multiple overlapping AgentRuns can produce ambiguous file changes. Use explicit association confidence and conservative defaults.
- **Content leakage.** Diffs and file contents are useful but sensitive. Keep RFC-012 summaries path/metadata-only.
- **Path escape mistakes.** Treat path normalization and symlink handling as a security boundary.
- **Git dependency drift.** Git is common but not universal. Keep detector availability explicit.
- **Scope creep into UI/audit.** Keep rendered review surfaces for M8 and durable audit for RFC-013.

## Resolved Decisions

- RFC-012 ships metadata-only filesystem snapshot detection. Git detection remains explicitly unavailable/unsupported pending the RFC-012 Git safety evidence.
- Per-file review decisions are deferred. `PartiallyAccepted` is ChangeSet-level state vocabulary and does not persist per-file or hunk decisions.
- Artifact references are currently opaque strings, while bounded summaries expose only their count. Durable reference semantics remain future work.

## Amendment 1: Change Lifecycle on `DetectedChangedPath`

**Status:** Authorised by the human owner 2026-08-11.
**Amendment type:** Additive (`ChangeLifecycle`, a new field) **plus one breaking removal** (`ChangePathKind::Deleted`). The breaking half was taken deliberately; see §Version consequence.

### What is authorised

1. **`ChangeLifecycle { Added, Modified, Deleted }`**, carried on `DetectedChangedPath` alongside the existing `kind`.
2. **Removal of `Deleted` from `ChangePathKind`**, leaving `{ File, Directory, Symlink, Other }`.

### Why it is needed

RFC-024 §Correction delivers three different things per change kind: full content for an added file, the fact of deletion for a removed one, and current content **explicitly labelled not a diff** for a modified one. Filling that in requires telling Added from Modified.

`DetectedChangedPath` cannot. `changed_paths_between` branches on exactly this distinction and then discards it — the "present in baseline and current" arm and the "absent from baseline, present in current" arm both produce `{ relative_path, kind: after.kind }`. `DetectedChanges` exposes `baseline_snapshot_ref: Option<String>`, not the baseline entries, so it is not recoverable downstream either.

Neither substitution is acceptable. Treating every `File` change as Modified makes the Added case unreachable and mislabels a genuinely new file as an unresolvable modification. Treating them all as Added ships a real modification without the not-a-diff label — the exact overclaim RFC-024's own correction was written to prevent.

### The underlying defect this corrects

`ChangePathKind` conflated two orthogonal axes. `File`, `Directory`, `Symlink` and `Other` answer *what kind of thing is this*. `Deleted` answers *what happened to it*. Deletion got a variant in the kind enum because it was the easy case to notice, and addition then had nowhere to go — which is why the model could express one lifecycle state and not the others.

Adding `ChangeLifecycle` while leaving `ChangePathKind::Deleted` in place would make `{ kind: Deleted, lifecycle: Added }` representable and meaningless, in a model that decides whether a user is told "this is the whole change" or "this is not a diff." Removing the variant makes each enum mean exactly one thing and the contradiction unconstructable.

### Why no new RFC

**No new detection capability, and no content read.** The distinction is already computed inside `changed_paths_between`; this preserves information already derived rather than deriving anything new. Lifecycle is metadata, so RFC-012 §Design Principles 2 ("Summaries must not include file contents… Metadata first") is unchanged and unweakened.

Same shape as RFC-006 Amendment 1: a narrow exposure of state that already exists transiently. Contrast the diff *content* model, which was correctly **not** an amendment — it read file content, which RFC-012 deliberately deferred to a separate reviewed policy.

### Constraints inherited, unchanged

- Metadata-only detection. Lifecycle carries no content and no hash.
- Git detection remains unavailable/unsupported pending its own safety evidence.
- `ReviewBaselineEntry` is untouched — this amendment does not add content capture, and RFC-024 §Correction records why capturing before-content at baseline was rejected.

### Version consequence

Removing a public enum variant is a breaking change to `tekstide-core`, published at `0.6.0`. **The owner authorised it explicitly on the grounds that dead code harms future maintenance and extensibility.** The next release carrying this is therefore `0.7.0`, not `0.6.1`.

Footprint at the time of authorisation: two consumers of `ChangePathKind::Deleted` outside `change_detection.rs`, both in `project/diff/tests.rs`, both written the same week by RFC-024 PR-024-B.
